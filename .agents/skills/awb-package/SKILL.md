# Draft a delivery package

Package one investigation only after the user explicitly requests package work. Routine analysis, record maintenance, and revalidation flags never trigger packaging.

Resolve every repository path from the project root and every bundled asset path relative to this `SKILL.md`. Keep the workflow portable: use repository conventions and available tools rather than assuming a language, backend, or global skill installation.

## Establish the package

Identify the investigation, package name, and requested action: create or revise the working draft, and whether the user also marks the package delivered. If the request could refer to multiple investigations, ask which one before changing package files.

Use the package name the user gives. Otherwise reuse the existing package's name, or for a new package derive a short, stable name from the investigation, such as its name plus a purpose word, and report it.

Read the [package contract](references/package-contract.md) for paths, shared formats, and complete consistency rules. Use one stable package per investigation unless another has an independent scope or delivery schedule. Copy only missing shared format files named in the contract from `assets/package-format/` into root `package-format/`; preserve existing files.

The mechanical work runs as three commands from the project root, described under **Commands** in the contract: `python3 src/awb.py draft-provenance` fills the manifest's producing and packaging state, `python3 src/awb.py export` writes chart and dataset files after the export checks, and `python3 src/awb.py check-draft` runs every mechanical draft check and rewrites the manifest inventory. Preserve customized project helpers and call the project copies.

For a new package, ask which audience-facing datasets to include and explicitly offer **none**. There is no default export set. For a revision, inherit the selection recorded in the current manifest unless the user changes it or it no longer fits the package scope. If it no longer fits, explain why and ask for a new selection before exporting data.

Read the **Audience** section of the investigation's `brief.md`: who will see or present the deck, what they already know, the decision they own, and the terms they use. `findings.md` is written for that audience. When the section is missing or blank, ask the user before drafting, and record the answer in the brief's **Audience** section, adding the section after **Purpose** when absent, as record maintenance.

## Gather the record

Choose the read path from the requested change:

- **New draft or changed analytical scope/results:** read the investigation's `brief.md`, `state.md`, `history.md`, analytical settings, and composition entry; the relevant portions of `foundation/sources.md`, `catalog.md`, `quality.md`, and `glossary.md`; and the existing draft manifest and latest release, when present. Changed results require separately authorized analytical work and recorded evidence before packaging.
- **Bounded narrative revision, including an omission or accepted caveat:** start with the current draft and manifest, the brief's **Audience**, current findings and flags in `state.md`, the requested change, and the evidence, history entries, and foundation entries relevant to it. Read the latest release portions and release date needed for both changes sections. Reuse recorded result provenance and exports. Expand to the rest of the brief, settings, composition entry, earlier history, and foundation records wherever scope, evidence, provenance, or consistency is missing or conflicting. `check-draft` derives the complete internal-name set from the project, so bounded reads never limit verification of the complete resulting draft.

Recover the business question, intended decision or exploratory purpose, audience, usefulness criteria, and evidence needed for the package contract. Include data limitations and errors affecting interpretation.

The records are written in internal vocabulary: view, table, and column names, settings keys, result IDs, and paths. `methodology.md` keeps that vocabulary. `findings.md` translates it for the audience under the translation rule in `package-format/findings-template.md`: glossary business terms in place of internal names, sources described by owner, content, and period, and exclusions and choices described by their effect.

Capture provenance for every field in `package-format/manifest-template.md`, covering both the represented analytical results and the packaging operation. A commit identifies code, not data. Run `python3 src/awb.py draft-provenance <investigation> <package> <result-id>...`, naming every result the package represents: it writes `producing_commit`, `producing_uncommitted_changes`, `inputs`, and `analytical_settings` from those results' evidence files, and `packaging_commit` and `packaging_uncommitted_changes` from the checkout, and leaves every other field as it was. Fill `scope` and the remaining fields yourself. When a represented result has no evidence file, the command writes nothing; record the producing state by hand from the investigation records or an earlier package manifest instead, never from the current `HEAD`, which describes the packaging checkout, not the results. Review what the command wrote against these rules. If the producing state included uncommitted changes, say that its SHA does not fully identify the producing code and record the changed paths or other available state evidence. If no commit existed and the evidence records `uncommitted` with the checksums of the producing files, record that value and those checksums as the producing commit, and say that no commit identifies the producing code. A package built from a dirty or uncommitted producing state is never described as reproducible. If a provenance field is unavailable, record it as unknown with the reason. Commit nothing on the user's behalf to make provenance look clean.

## Assemble the draft

Create the draft lazily at the paths in the package contract; revise those same files. A draft in an earlier format (a `figures/` directory, a narrative `findings.md`, or a journal and executive summary) is rewritten in the current format on its next revision, whatever the requested change: remove the obsolete files, rewrite `findings.md` as the deck outline, and write chart files from recorded results. Numbered releases stay as delivered. Adapt shared templates to the investigation; `findings.md` is the slide-by-slide outline of the deck under the slide rules in the findings template, and its **Answer** slide is the executive summary. Apply the contract's audience translation, matching finding headings, M365 boundary, and changes-section rules. Copy shared `m365-assembly.md`, fill **Files in this package** and **Audience** from the brief, and adjust only concrete package details. Preserve additional manifest fields from an established schema. Set `created_at` once, `revised_at` on every revision, and `status` to `draft`.

Export exactly the user-selected datasets, and the data for each chart `findings.md` specifies, with one call: `python3 src/awb.py export <investigation> <package> --chart <result>[:<columns>] ... --dataset <name>=<result>[:<columns>] ...`, or `--no-datasets` for an explicit selection of none. Give one `--chart` per **Chart N.** specification, in order. It reads each result's saved table under `investigations/<name>/results/`, keeps only the named columns, renames them and maps coded values with the display names in `foundation/display.toml`, rounds as that file's `[round]` table or `--round` says, runs the export checks, and only when they pass writes `charts/chart-N.csv`, `datasets/<name>.csv`, and the manifest's `charts`, `dataset_selection`, and `export_checks`. When a column lacks a display name it lists every gap at once and writes nothing: add the names to `foundation/display.toml`, taking them from the glossary, and rerun. It prints the header-to-source-column lines to paste into `methodology.md` and the `check_charts` result. These are audience-facing outputs, not intermediate handoffs; convenience extracts, temporary query dumps, and full database snapshots are out of scope. Choose the columns so the file holds exactly what the chart plots, interval bounds as their own columns; a choice made only for display, such as the highlighted group or a non-zero baseline, goes in the chart specification, not the data. A caveat on a dataset or column goes in the description of that dataset under **Supporting datasets** in `findings.md`, never into its values. A project with an established non-CSV export format exports by hand under the same rules.

An export serializes a recorded result and never reruns analysis. `export` runs `compare_evidence` from the project's `src/provenance.py` against each result's evidence, comparing the complete producing code, views, input publications/acquisitions, and resolved settings; a hand comparison never substitutes. When it reports `exports_blocked` it writes nothing: stop and report that the export would not serialize the represented result; changed results need separate analytical work. A revision that reuses every export runs no `export` and carries the recorded checks forward; `draft-provenance` fills the producing state either way.

Exact-rerun inputs or database snapshots are included only when the user explicitly chooses them.

For a narrative-only revision, reuse the existing result evidence, exports, and producing provenance. Update the narrative and package metadata without rerunning or reconstructing analysis. Run analytical code only when the user separately requests changed results. When a revision brings in facts not yet in the investigation records, such as a limitation or context the user supplies, record them in the investigation's `history.md` as record maintenance before or with the revision, so neither `findings.md` nor `methodology.md` states more than the records.

Findings awaiting revalidation may remain in the draft under the package contract's caveat rule. List each represented finding currently flagged in `state.md` under the manifest's `revalidation_flags`, with its current reason and every place the draft represents an affected conclusion, and disposition `none` until the user chooses. Preserve the user's recorded revalidate, omit, or release-with-caveat disposition across revisions while the finding and evidence remain materially the same; when the flag's reason changes, record the new reason and reset its dispositions to `none`. Packaging never reruns analysis on its own; an export under the check above is not a rerun.

Verify the entire resulting draft against every rule in the [package contract](references/package-contract.md), including flags outside the edited passage. Once every other draft file is final, run `python3 src/awb.py check-draft <investigation> <package>`. It derives the complete names set from the project, runs the findings `check` and `check_charts`, rewrites the manifest `inventory`, and runs `verify`; it exits 0 only when all of them pass. Repair the draft and rerun it until it passes and every structural and caveat rule holds. Report its helper rows unchanged; the complete record, including the names set, stays in its `record` file.

## Delivery milestone

When the user marks the package delivered or requests an equivalent delivery milestone, finish any draft revision requested with it, then invoke the sibling [`awb-release`](../awb-release/SKILL.md). That skill verifies the draft's structure, settles revalidation dispositions, re-verifies the draft in full, and preserves the numbered release; this skill never creates a `released/` directory.

## Report

Finish by reporting the draft path, the audience `findings.md` is written for, included datasets, the charts and the result each serializes, provenance gaps, and unresolved caveats. Tell the user it is a working copy that the next revision overwrites; only marking it delivered preserves it as a numbered release. When a represented finding is flagged for revalidation without an applicable recorded disposition, note that `awb-release` will ask for a disposition for each before releasing.
