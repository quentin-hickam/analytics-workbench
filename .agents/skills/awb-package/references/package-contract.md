# Package contract

Repository paths are relative to the project root.

## Layout and formats

All revisions use `deliveries/<investigation>/<package>/draft/`. Numbered `released/001`, `released/002`, … siblings are frozen. Release storage holds a copy of each at `<location>/<investigation>/<package>/<n>/`, without the `released/` folder. Each draft contains:

```text
START-HERE.md                # written by check-draft: what to send, what builds the deck, what stays internal
findings.md                  # audience-facing deck outline; sole slide-content source
methodology.md               # internal reference; kept out of the deck
methodology-note.md          # optional audience-facing account of method; delivered beside the deck
deck-rules.md                # how any builder builds the deck from findings.md and charts/
assembly/m365.md             # Microsoft 365 Copilot specifics
manifest.json
charts/                      # only when findings.md specifies charts: chart-N.csv per chart
datasets/                    # only when datasets were selected
```

`START-HERE.md` is plain text telling whoever holds the package or a release what to send the audience (the deck once built, `methodology-note.md` when present, `datasets/`), what builds the deck (the attach list and prompt from `assembly/m365.md`), and what stays internal (`methodology.md`, `manifest.json`, `deck-rules.md`). `check-draft`, not `export`, writes it, before the inventory: `export` runs before the narratives and any methodology note are final, and `check-draft` runs last, on the files as they ship. `--verify-only` verifies it like any other file and refuses a draft that lacks it, since every release includes it.

Shared formats live in root `package-format/`: `findings-template.md`, `methodology-template.md`, `methodology-note-template.md`, `deck-rules.md`, `assembly/m365.md`, and `manifest-template.md`. They are shared across investigations; preserve existing files. The project's copies govern: `findings-template.md` holds the translation rule and slide rules, and `manifest-template.md` the manifest fields.

`methodology.md` is the complete authoritative analytical account in internal vocabulary. `findings.md` derives from it for the brief's **Audience**, states nothing it does not support, and is the slide-by-slide outline of the deck and the only source of slide content. The optional `methodology-note.md` derives from it too: a short plain-language account of method, sources, definitions, exclusions, and limitations for the same audience, under the findings translation rule. It states nothing methodology does not support, travels beside the deck like datasets, and is not attached to the builder.

When releases exist, findings adds **What changed since the last version** against the latest release, identifying its delivery date from manifest `released_at`.

The deck opens with the title slide and then the **Answer** slide, which is the executive summary; the two stay separate, and the builder writes no summary of its own. Those slides and the rest before an optional closing **Appendix** section are the main sequence; the appendix's slides follow a divider slide the builder adds. Any builder builds the deck from `findings.md` and draws each chart from its file under `deck-rules.md`, with its own steps in its file under `assembly/`; datasets travel beside the deck. Microsoft 365 Copilot's PowerPoint agent is the builder the package ships for, under `assembly/m365.md`. The builder consults methodology for reasoning only. Findings, methodology, chart files, and datasets stay authoritative upstream: substantive revisions return through the draft, and layout and polish made in the deck are not carried back to the workbench.

## Ledger storyline

Read the complete question tree: each question has an existing `parent` ID or an empty root parent, and `priority` is `must`, `should`, or `could` (default `should`). Walk roots and children depth-first, sorting siblings by priority in that order, then by question ID. A finding slide's matching methodology section identifies its represented results through result IDs or evidence links; each result's recorded settings `answers` identifies the ledger questions it answers. Select the highest-priority question the slide answers, breaking a tie by its position in that depth-first walk. Order finding slides by that selected question's priority, then its walk position; the main sequence's finding slides and the appendix's each follow this order. Slides tied on both retain their order; slides answering no ledger question go last and are named in the report's informational `unlinked_findings` list.

This ledger-derived order is the default the headline checkpoint proposes. An order of finding slides the user approves instead is recorded in the manifest's `presentation_order` and decides: every finding slide, main sequence then appendix, follows it, and it lists each finding heading once. Ledger priority and parent keep deciding **Open questions** membership, so a presentation reorder never changes them. `storyline` rows report each finding slide out of place, those outside the longest run already in order, so moving one slide reports that slide alone, and a `presentation_order` that misses or repeats a finding slide or names a heading none has.

**Open questions** follows **Limitations and open caveats**, before **What changed since the last version** when that slide exists. When **Limitations and open caveats** is under **Appendix**, **Open questions** stays in the main sequence where that slide would have stood: after the last finding, **Implications**, or **How we know** slide. Include it if and only if unanswered `must` questions exist: open or parked questions, plus answered data questions whose answering findings include any flagged (`revalidation-needed`) or superseded finding. The latter display as `answered (awaiting recheck)`, or `answered (provisional, awaiting recheck)` when none of those findings is supported or was before its flag, while their stored status remains `answered`. Declined or superseded questions are set aside and excluded. Give each required question exactly once as a top-level bullet, using its exact `audience` wording when set, otherwise its question `text`; inline Markdown accepted by the outline reader is allowed. Keep IDs and owner commentary out of those bullets, and use no nested bullets. The slide is exempt from the five-bullet limit so every required question fits; report the count when it exceeds five. `open_questions` rows report presence, placement, and membership violations. This is exact text comparison, not a paraphrase or audience-language classifier; `awb-package` sets audience wording where the text is not in the audience's words.

A new draft, or a changed storyline, passes the headline checkpoint: in **preview-and-wait** the user approves or reorders the title slide and every headline, in storyline order, before the full slides are written; in **draft-then-review** the full draft comes first, and the draft report shows its headlines, marked provisional, for approval or reorder. The mode is the first of these that applies: the mode the request states; **draft-then-review** when the request supplies the storyline or asks for the full draft; the mode the brief's **Audience** section records; **preview-and-wait**. A consequential open choice stops the draft in either mode and is asked with the headlines. A revision retaining the storyline skips this checkpoint.

## Structural consistency

Every rule holds for the complete draft:

- `findings.md` follows the slide rules in `package-format/findings-template.md` (`outline`): a title slide, one headline of at most 15 words, at most five bullets (except **Open questions**), at most one chart, and a closing **Notes:** paragraph per slide, and nothing outside a slide. The required slides, once each and in this order, are the title, **Answer** right after it, at least one finding slide in the main sequence, **How we know**, and **Limitations and open caveats**; one closing **Appendix** of `###` slides may hold findings, **How we know**, **Limitations and open caveats**, and **Supporting datasets**, a required slide there still counting, and **How we know** before **Limitations and open caveats** whenever both stand in the same part. Its finding order and **Open questions** content follow **Ledger storyline** (`storyline`, `open_questions`).
- `findings.md` stands alone for its audience: context, answer, findings with evidence and contrary results, plain-language method, limitations, and caveats need no earlier release, methodology, or edits in the deck. `findings: []` is the mechanical check only.
- `methodology.md` stands alone as the analytical account: scope, sources, method, settings, validation, findings, evidence, contrary results, limitations, and caveats need no earlier release or investigation records. Include methodological mistakes that changed understanding; execution attempts that changed no understanding stay in code history.
- The narratives, `findings.md`, `methodology.md`, and `methodology-note.md` when the draft holds it, agree in claims, numbers, qualifications, and caveats. Every number in any of them traces to a represented result or is listed in the manifest's `allowed_numbers` with its reason (`numbers`); a **Claim strength:** line the `claims` check accepts repeats the `state.md` Claim cell, so its numbers are not read. That check proves each number is recorded somewhere, not that the narratives agree, so the [draft review](review.md) confirms that every claim in `findings.md` and in the note, with its numbers, traces to the matching claim in `methodology.md`. A sentence asserting that something was checked or verified, reconciles, sums or adds up to, or matches cites the check that establishes it, covering all it asserts: a result ID, an evidence path, or a foundation quality ID with its scan in `methodology.md`, and the check in plain words in `findings.md` and the note; the draft review confirms it. A tolerance is stated only where it was set before the data was seen, and only in `methodology.md` and speaker notes; an exact check says "exactly" or "every row", and a tolerance chosen after seeing the result is not one. The note follows the findings translation rule (`findings`). Every `###` finding heading in findings has exactly one methodology section with identical heading text, and no two finding slides share a heading (`headings`); methodology repeats verbatim, in text that renders, the question each represented result answers (`questions`). Every narrative keeps to the Markdown subset the checks read as it renders, so no form hides text from them or moves it between slides (`markdown`; the subset is in [helpers](helpers.md)).
- No slide in findings is worded more strongly than its claim strength (`claims`), read from the rendered `state.md` Claim cells of the manifest's `results`. A checked slide is read whole: its heading (a finding slide's headline), bullets, **Caveat:** lines, chart specification, and notes. A `###` finding slide takes the weakest claim among the results its methodology section cites by ID or evidence link outside comments, or among all represented results when it cites none; the title, **Answer**, **Implications**, and any other slide stating conclusions take the strongest. Below `causal`, wording such as drives, causes, because of, due to, leads to, or impact of is refused: reword it, since only a finding recorded `causal` with its design basis supports it. A verb of change with an agent as its subject ("the carrier raised late orders", "discounts cut them") is not on the list, so the [draft review](review.md) catches it. **How we know**, **Limitations and open caveats**, **What changed since the last version**, and **Supporting datasets** are not checked, under **Appendix** too; an appendix finding slide is checked like any other. `methodology-note.md` is read whole at the strongest represented claim, as the **Answer** slide is. Each methodology finding section has exactly one `**Claim strength:**` line, opening a top-level paragraph at the start of a line (helpers.md states the reading), naming its slide's claim as a `state.md` Claim cell does; a causal one is the Claim cell, design basis included, that every result the section cites records, so results of different designs need separate findings. The reference therefore states what the record holds.
- Commands write every manifest field except `allowed_numbers`, `presentation_order`, and the `results` entry and producing state of a result without evidence; in `revalidation_flags` you fill `represented_in` and the user's `disposition`. A field recorded by hand follows `package-format/manifest-template.md`.
- The manifest `inventory` matches every draft file's byte size and SHA-256, except its own path-only row (`verify`).
- `charts/` matches the chart specifications in `findings.md` (`charts`): numbered in order, each with its file, a form from `deck-rules.md`, and a **Data:** line naming that form's roles by columns the file holds and naming every column it holds. Each chart file serializes a recorded result, and the manifest's `charts` and the methodology name that result. Each file equals that result's saved table under the row selection, labels, percent scaling, and rounding its `charts` entry records, so rows are selected with `--chart`, never by editing the file.
- Chart and dataset files show rounded numbers: `export` refuses a column showing more than four decimal places that `[round]` in `foundation/display.toml` or `--round` does not cover, and `[percent]` shows fractions as percents. The manifest's `charts` and `dataset_selection` entries record both, and `methodology.md` states them.
- `datasets/` and the manifest match the recorded audience-facing selection, including explicit `none`. Headers use glossary display names; methodology maps each to its source column. Dataset and column caveats go under findings' **Supporting datasets**, leaving values as recorded.

## Revalidation caveats

`check-draft` refuses drift in the rendered table and names `state render`; with no `findings.json` any row is drift; a project helper without `findings_drift` needs `awb-init` repair (`install_helpers.py --upgrade`). Flags still come from the rendered `state.md` rows.

The manifest's `revalidation_flags` is `none` or one entry per finding the investigation's `state.md` currently flags (`unmatched_flags` lists the ones it lacks): `{finding, reason, represented_in, disposition}`. `finding` and `reason` are exactly as that row writes them. `represented_in` lists every place the draft represents an affected conclusion, each a short description such as `findings: <slide headline>`, `methodology: <section>`, `methodology-note: <section>`, `chart 2`, or `dataset late-closures: <column>`; or it is `none` when the draft represents none. `disposition` is one of `none`, `revalidate`, `omit`, or `release_with_caveat`: required when `represented_in` lists places, optional when it is `none`. Each represented flagged finding is listed as unresolved under findings' **Limitations and open caveats**.

Each represented conclusion carries a nearby caveat unless the disposition omits the conclusion: beside claims in each narrative that states them, in a chart specification's **Caveat:** and **Alt text:** lines in findings, or in the dataset or column description under **Supporting datasets**. Findings uses the template's **Awaiting revalidation:** prefix with a plain-language reason, on every slide where the conclusion appears.

A recorded disposition applies while its finding and reason match the current `state.md` row exactly; a new or changed reason reopens it. A draft holds `none` until the user chooses. Release requires `omit` or `release_with_caveat` for every represented flag; `revalidate` pauses the release for separately authorized analytical work.

## Commands

The commands' verdicts settle every mechanical rule; summarize their outcomes in chat. Run each from the project root; `python3 src/awb.py <command> --help` gives its arguments, output keys, and exit status. To diagnose a helper's rows, such as a name `check-draft` reports that is not internal, read [helpers](helpers.md).

- `export <investigation> <package>` writes the chart and dataset files, `charts`, `dataset_selection`, `export_checks`, and the producing and packaging state, creating the manifest when absent; a call with only `--result` refreshes provenance and leaves exported files untouched. A `--chart` selects rows with `@first=<n>` or `@where=<column>=<value>[,<value>]`, a closed grammar [helpers](helpers.md) states. Names, labels, rounding, and percents come from `foundation/display.toml`; gaps come back with `display_stub` and `round_stub`, and `label_warnings` names a column whose one name labels results that answer different questions. It serializes only when every `--chart` and `--dataset` result passes `compare_evidence`, otherwise reporting `exports_blocked`; a `--result` is recorded without that check. It writes nothing when any evidence is missing.
- `review-rules check <investigation> <package>` lists every rule in `foundation/review-rules.md` with the narrative lines its pattern matches, `methodology-note.md` included when the draft holds it, grouped by the rule's scope into one entry per line, slide, or file, leaving out a rule kept for another package, writing nothing; `review-rules add --confirmed`, run only once the user says yes, appends the next numbered rule, `--scope slide` or `--scope document` sets its scope, `--package <investigation>/<package>` keeps it for that package, and its `warnings` name each number it shares with a draft. `review-receipt record` keeps a review's report and what it read beside the draft, and `review-receipt show` compares that record with the draft, writing nothing; `check-draft` shows its status, and `release` refuses unless it is `current`. [Draft review](review.md) says who runs each.
- `check-draft <investigation> <package> [--verify-only]` checks the whole draft against every internal name the project defines, the slide rules and required slides, the finding order (`presentation_order`, else the ledger's) and **Open questions** slide, the chart specifications and files, the headings, the Markdown subset, causal wording against claim strength, each manifest `results` question in methodology, every number in the narratives against the represented results, the inventory (rewritten unless `--verify-only`, which writes nothing), and `state.md`'s current flags. Without `--verify-only` it first writes `START-HERE.md`. `unlinked_findings`, `slides` (main and appendix slide counts), `note_length` (a note more than 10% over the brief's `Methods note length: about <n> words`), and `draft_markers` (draft wording in the title, subtitle, headings, or title notes, which `awb-release` asks about) are informational; rows from `methodology-note.md` name it; `storyline` and `open_questions` violations fail the check. `names_problems` means that name set is incomplete, and `numbers_problems` the recorded values: repair the cause and rerun.
