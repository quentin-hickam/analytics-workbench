# Package contract

Read for every draft creation, revision, or release verification. Repository paths are relative to the project root. This contract governs structure and consistency; [awb-package](../SKILL.md) governs drafting and [awb-release](../../awb-release/SKILL.md) governs delivery.

## Layout and formats

All revisions use `deliveries/<investigation>/<package>/draft/`. Numbered `released/001`, `released/002`, … siblings are immutable. The `audit/` sibling holds the complete records the package commands write; it is never part of a draft or release. Each draft contains:

```text
findings.md                  # audience-facing deck outline; sole slide-content source
methodology.md               # internal reference; never shown in the deck
m365-assembly.md
manifest.<project-format>
charts/                      # only when findings.md specifies charts: chart-N.csv per chart
datasets/                    # only when datasets were selected
```

Shared formats live in root `package-format/`: `findings-template.md`, `methodology-template.md`, `m365-assembly.md`, and `manifest-template.md`. Preserve existing shared files and established manifest schemas; templates are shared across investigations. Read the project's findings translation rule and manifest field list when drafting or validating; their initial templates are [findings-template.md](../assets/package-format/findings-template.md) and [manifest-template.md](../assets/package-format/manifest-template.md).

`methodology.md` is the complete authoritative analytical account in internal vocabulary. `findings.md` derives from it for the brief's **Audience**, states nothing it does not support, and is the slide-by-slide outline of the deck and the only source of slide content, following the slide rules in the findings template. Use glossary business terms in findings, describe sources by owner/content/period and analytical choices by their effect. The brief records readers, prior knowledge, owned decision, and terms they use. A missing or blank **Audience** must be resolved with the user and recorded in the brief before drafting.

When releases exist, both narratives retain their complete account and add a concise changes section against the latest release: findings' **What changed since the last version** identifies its delivery date from manifest `released_at`; methodology's **Changes since previous release** names its release number. Assembly instructions list the files and carry the brief's **Audience**.

The **Answer** slide in `findings.md` is the executive summary; M365 writes none. In the Microsoft 365 Copilot app, the PowerPoint agent builds the deck from `findings.md` and draws each chart as a native chart from its file under the chart rules in `m365-assembly.md`; datasets are delivered beside the deck. M365 can consult methodology for reasoning only, never as slide content. Findings, methodology, chart files, and datasets stay authoritative upstream. Substantive revisions return through the draft; deck edits are never reconciled back into the workbench.

## Structural consistency

Verify all of these for the complete draft:

- `findings.md` stands alone for its audience: context, answer, findings with evidence and contrary results, plain-language method, limitations, and caveats require no earlier release, methodology, or M365 edits. `check-draft` runs the [findings helper](findings-helper.md) `check` on it with `names` containing the investigation/package names, every view/table name the investigation reads, every settings key, and every result ID cited in its records, derived from the project even for a bounded revision. Repair until it returns `[]`; a hand check never substitutes.
- `methodology.md` stands alone as the analytical account: scope, sources, method, settings, validation, findings, evidence, contrary results, limitations, and caveats require no earlier release or investigation records. Include methodological mistakes that changed understanding; execution attempts that changed no understanding stay in code history.
- The narratives agree in claims, numbers, qualifications, and caveats. Every `###` finding heading in findings has a methodology section with identical heading text.
- The manifest uses shared fields and records unknowns with their reasons. A producing commit describes result code; packaging `HEAD` never substitutes. Dirty, `uncommitted`, or unknown producing state is never called reproducible. Without user-selected exact-rerun inputs, provenance locates the producing state but does not guarantee an exact rerun.
- The manifest `inventory` exactly matches every draft file's byte size and SHA-256, except its own path-only row. The [manifest helper](manifest-helper.md) `verify`, run by `check-draft`, must return no discrepancies. Hand comparisons never substitute. Release verification uses `check-draft --verify-only`, which reads the recorded rows without regenerating them to hide differences.
- `charts/` matches the chart specifications in `findings.md`: the [charts helper](charts-helper.md) `check_charts`, run by `check-draft`, must return `[]`. Each chart file serializes a recorded result under the export check, and the manifest's `charts` and the methodology name that result.
- `datasets/` and the manifest match the recorded audience-facing selection, including explicit `none`. Headers use glossary display names; methodology maps each to its source column. Header renaming preserves values. Dataset/column caveats belong under findings' **Supporting datasets**, never in values. Exact-rerun inputs or snapshots require explicit user selection.

## Revalidation caveats

Check current investigation flags, not only flags copied into the draft. For every represented finding awaiting revalidation, the manifest records its current reason and every affected narrative passage, chart, dataset, or column. List the finding as unresolved under findings' **Limitations and open caveats** and methodology's **Revalidation status**.

Each represented conclusion carries a nearby caveat unless a recorded disposition omits it: beside claims in both narratives, in a chart specification's **Caveat:** and **Alt text:** lines in findings, or in the dataset/column description under **Supporting datasets**. Findings uses the template's **Awaiting revalidation:** prefix with a plain-language reason, on every slide where the conclusion appears.

A disposition remains applicable only while the finding, evidence, and flag reason remain materially the same; new or changed flags reopen the choice. Drafting permits `none` pending the user's choice. Release requires an applicable disposition for every affected place; revalidation pauses release for separate analytical work. Release first checks structural rules, settles dispositions, then checks every rule here, and the `release` command reruns `check-draft --verify-only` even if nothing changed.

## Commands

Run from the project root. Each prints one line of JSON and writes its complete record under `deliveries/<investigation>/<package>/audit/`, named by the `record` key. Only JSON manifests are automated; the manifest is the draft's single `manifest*` file, `manifest.json` when there is none, or the path given with `--manifest`.

- `python3 src/awb.py check-draft <investigation> <package> [--verify-only]` derives the names set from the project: the investigation and package names; view and table names created or read in `foundation/views/*.sql` and in the views the investigation's evidence cites, without CTE names or table functions; the investigation's settings keys (`settings.toml` and the settings files and resolved settings its evidence records): top-level keys and the dotted path of every nested key, but not a nested key's bare name, which is usually a plain word; and the result IDs of `investigations/<investigation>/evidence/*.json` and the evidence links in its brief, state, and history. It runs `check` and `check_charts`, rewrites the manifest `inventory` unless `--verify-only`, and runs `verify` against the recorded rows. Output: `names` (set size), `names_problems` (anything that leaves the set incomplete, such as unparsable settings), `findings`, `charts`, and `verify` (each helper's rows unchanged), `errors`, and `passed`. It exits 0 only when every list is empty. With a non-JSON manifest it runs the findings and chart checks, reports that the inventory and `verify` must be run by hand, and fails.
- `python3 src/awb.py draft-provenance <investigation> <package> <result-id>... [--export-checks]` writes `producing_commit`, `producing_uncommitted_changes`, `inputs`, `analytical_settings`, `packaging_commit`, and `packaging_uncommitted_changes`, and with `--export-checks` replaces `export_checks` with each listed result's `compare_evidence` output. It leaves every other field untouched and creates `manifest.json` when the draft has none. It writes nothing and exits 1 when an evidence file is missing or unreadable, or when any comparison fails (`exports_blocked`).
- `python3 src/awb.py export <investigation> <package> [--chart RESULT[:COLUMNS]]... [--dataset NAME=RESULT[:COLUMNS]]... [--no-datasets] [--round COLUMN=PLACES]...` reads each result's saved table at `investigations/<investigation>/results/<result>.csv`, keeps the named columns in order, renames them and maps coded values with `foundation/display.toml` (`[columns]`, `[values.<column>]`, `[round]`), rounds half up, and runs `compare_evidence` for every result. Only when every column has a display name and every comparison passes does it write `charts/chart-N.csv` (in `--chart` order, through `write_charts`), replace `datasets/` with the named files, and record `charts`, `dataset_selection` (or `none`), and `export_checks` for those results in the JSON manifest. Output: `charts`, `datasets`, `export_checks` (`results`, `failed`), `exports_blocked` when blocked, `methodology_lines` (each header with its source column), `check_charts`, and `errors`. It exits 0 only when written and `check_charts` is empty. Writing chart files needs pandas.
- `python3 src/awb.py release <investigation> <package>` refuses, creating nothing, unless `check-draft --verify-only` passes and every place under `revalidation_flags` has the disposition `omit` or `release_with_caveat` (`none` and `revalidate` both refuse, listed under `dispositions`). It then copies the draft to the next numbered release, stamps the copy's `status`, `release_number`, `released_at`, and `prior_release`, and handles storage from the README's `Released packages are kept at` line. `storage.status` is `copied` (with `compare_trees` rows, empty on success), `mismatch`, `conflict` (the destination exists; nothing is overwritten), `copy failed`, `unreachable` (a URL, prose, or a missing path; `instruction` names the exact copy), `unrecorded` (with an instruction), or `none chosen` (with the only-copy warning). It exits 1 when it refuses or on `mismatch`, `conflict`, or `copy failed`.
