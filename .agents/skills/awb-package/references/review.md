# Draft review

`awb-package` runs this review before its final `check-draft`, and `awb-release` before `release`. The reviewer reads the draft and reports; the agent that wrote the draft repairs. Repository paths are relative to the project root.

## Launch

Start a fresh subagent, so the agent that wrote the draft does not review it. Give it the investigation, the package, the absolute project root, and the absolute path of this file, and, for a scoped re-review, the prior report and the diff **After the review** describes, and tell it to follow **Brief**. Scope its tools by host:

- In VS Code Copilot, use `runSubagent` under the installed user-level `awb-package-reviewer` custom agent, whose definition ships at `../assets/awb-package-reviewer.agent.md`. It has only file read/search and `awb/read`; run the check with `command: "review-rules"`, `project`, `investigation`, and `package`. If the reviewer agent is unavailable, stop and tell the user to install it per the README and choose the Local session target; a failed `awb/read` call is a command problem the reviewer reports. Never substitute an unrestricted subagent or `awb/*`.
- In Claude Code, use a subagent type without edit tools, such as the built-in `Plan`, or a custom one whose `tools` are `Read`, `Grep`, `Glob`, and `Bash`; a skill's `allowed-tools` only pre-approves tools and restricts nothing.
- In Codex, whose subagents inherit the session's sandbox and tools, start a fresh subagent all the same; the limit to read tools is then the brief's instruction alone.
- Only in a host with no subagents, follow **Brief** yourself, changing no file and running no command that writes until the report is complete, then act on it as **After the review** says. In `awb-package` that is a self-review by the agent that wrote the draft.

Bash in the Claude Code branch can still write, and Codex inherits tools, so those limits are conventions plus tool scoping where available. The Copilot custom agent has no shell or write tool.

## Brief

You review the package draft at `deliveries/<investigation>/<package>/draft/`. Its narratives are `findings.md`, `methodology.md`, and `methodology-note.md` when the draft holds it. Report findings; never fix them, and change no file. Run no command that writes: the only `awb.py` command you run is `python3 src/awb.py review-rules check <investigation> <package>`, which writes nothing (in Copilot, use the MCP call in **Launch**), and where the host reads files only through a shell, read-only commands such as `cat`, `sed -n`, and `rg` are reads. Report every violation and narrative problem in this one pass, quoting each; the caller settles them all before the next review.

1. Run that command. Read `foundation/review-rules.md` when its `rules_file` is not `none recorded`, then the draft's narratives and the `revalidation_flags` in `manifest.json`.
2. Judge every rule the command lists that is not `retired`, against every narrative. A `matched` line is a candidate to judge, not a verdict; `no match`, `no pattern`, and `unchecked` rules are judged by reading. A rule's scope is what one violation covers: one line (`line`, the default), one slide (`slide`; in `methodology.md` and the note, one section under a `#`, `##`, or `###` heading), or one file (`document`); the command lists each match of a `slide` or `document` rule as that slide or file with the lines it matched, up to 20, and counts any more as `more_lines`, which you find by reading.
3. Check what no command checks: the narratives carry the same qualifications and caveats; no finding is worded more strongly than its claim strength, including wording off the `claims` check's list, such as a verb of change with an agent as its subject ("the carrier raised late orders"); every `represented_in` place of each `revalidation_flags` entry carries its caveat, or its omission when the disposition is `omit`; every claim in `findings.md`, with its numbers, traces to the matching claim in `methodology.md`, and `methodology-note.md` states nothing `methodology.md` does not support, since `check-draft` proves only that each number is recorded somewhere; and every sentence in any narrative that asserts that something was checked or verified, reconciles, sums or adds up to, or matches cites the recorded result or check that establishes it, covering all it asserts, such as every year rather than some: in `methodology.md` a result ID or evidence path, whose evidence you read to confirm; in `findings.md` and the note, the check in plain words, with its tolerance, that `methodology.md` cites. A sentence without one is a narrative problem. This pairs with the warning `awb.py state finding` gives on a finding whose wording asserts a reconciliation or a completed check that no passing check records.
4. Report exactly this, and nothing else, since the caller must account for every rule verdict and diagnostic before summarizing them in chat:
   - one line per rule in the command's order: `<ID> pass`, `<ID> retired`, or `<ID> violation <severity> <file>:<line> "<short quote>"`, with the rule's `error` or `warning`, one line per violation; a `slide` rule's violation is cited at its slide or section's heading line and a `document` rule's at its first offending line, quoting every offending line in it;
   - one line per step 3 problem: `narrative <file>:<line> "<short quote>" <what is wrong>`;
   - the command's `problems` and `errors` verbatim, or `command failed` with its output when it did not run; and
   - a last line, `review: clean` when there is no violation, no narrative problem, and the command exited 0, or otherwise `review: <v> violations (<e> error), <n> narrative problems, <c> command problems`, where command problems count the `problems` and `errors` entries, or 1 when the command failed.

When the caller gives you a prior report and a diff, the review is scoped. Run the command as step 1 says, then judge steps 2 and 3 only on the diff's changed lines (for a `slide` or `document` rule, on each slide or file that holds one), the places of each changed `revalidation_flags` entry, and each violation and narrative problem the prior report lists, confirming each is repaired; judge each rule added or changed since, as the diff of `foundation/review-rules.md` shows, against every narrative in full. Report as step 4 says, with `<ID> pass` for each rule with no violation in that scope, and open the last line with `review (scoped):` instead of `review:`.

## After the review

A review is passed when its last line reports no `error` violation, no narrative problem, and no command problem, and the user has accepted every `warning` violation; anything else blocks completion and release. Only a full review, whose last line opens `review:`, can complete a request or a release; a scoped re-review, whose last line opens `review (scoped):`, never does.

In `awb-package`, repair every `error` violation, every narrative problem, and every command problem, and repair a `warning` violation or report it for the user to accept. A command problem is an unavailable or failed `awb/read` call, remedied by registering the `awb` server or choosing the Local session target; a missing `findings.md` or `methodology.md`, or a narrative that cannot be read, repaired in the draft; or a malformed section of `foundation/review-rules.md`, repaired in place without changing any rule ID; ask the user when a broken rule's intent is unclear. A review is stale once, after it, the narratives or `foundation/review-rules.md` change, or a `revalidation_flags` entry in `manifest.json` is added or removed or changes its finding, reason, `represented_in`, or whether its disposition is `omit`; a stale review is run again. Since the reviewer reports in one pass, settle everything it reports, as above, before the review runs again. `awb-release` repairs nothing and acts as its **2. Review** says.

Within one `awb-package` request, the review run again after repairs may be a scoped re-review: give the reviewer the prior report and a diff of every change since it, in the narratives, `foundation/review-rules.md`, and `revalidation_flags`, each changed line with its file and line number. The draft sits in the Git-ignored `deliveries/` folder, so Git keeps no reviewed version to diff against. Instead, each review leaves a copy of what it read, the draft's `findings.md`, `methodology.md`, `methodology-note.md` when the draft holds it, and `manifest.json`, with `foundation/review-rules.md`, in a scratch folder outside the draft, such as one in the system's temporary directory. For a scoped re-review, first make the diff against the copy the prior review left, `diff -u <copy> <current file>`, or `git diff --no-index`, for each of those files, so it holds every change since the prior review, a hand edit by the user included, rather than the changes the writer recalls. Then, for every review `awb-package` launches, full or scoped, and after any scoped diff is made, copy those files to the scratch folder, replacing the copy an earlier review left. When no copy of what the prior review read was kept, the next review is a full one. A scoped re-review can miss a problem a repair caused elsewhere, such as a renamed heading that breaks agreement, so a full review is still required before the request's final `check-draft`, and `awb-release` always runs the full review.

When the user corrects a draft while reviewing it, decide whether later drafts could repeat the mistake. If they could, record the correction as a rule before repairing, so every later review checks it: `python3 src/awb.py review-rules add --area <area> --severity <error or warning> --rule "<what every draft must do>" --fix "<how to repair it>" [--pattern '<regex>'] [--scope slide|document]`. The area names what the rule governs, such as `periods` or `metric-definitions`; give a pattern when one line of text can show the violation, and a scope when one violation is a whole slide or file. Report the new ID. A correction that applies to this draft only, such as a preferred wording on one slide, is an edit, not a rule.
