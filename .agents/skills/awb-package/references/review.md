# Draft review

`awb-package` runs this review before its final `check-draft`, and `awb-release` before `release`. The reviewer reads the draft and reports; the agent that wrote the draft repairs. Repository paths are relative to the project root.

## Launch

Start a fresh subagent, so the agent that wrote the draft does not review it. Give it the investigation, the package, the absolute project root, and the absolute path of this file, and, for a scoped review, the prior report and diff from `review-receipt show` or the instruction to read them with it, and tell it to follow **Brief**. Scope its tools by host:

- In VS Code Copilot, use `runSubagent` under the installed user-level `awb-package-reviewer` custom agent, whose definition ships at `../assets/awb-package-reviewer.agent.md`. It has only file read/search and `awb/read`; run the check with `command: "review-rules"`, `project`, `investigation`, and `package`, and read a scoped review's prior report and diff with `command: "review-receipt"` and the same arguments. If the reviewer agent is unavailable, stop and tell the user to install it per the README and choose the Local session target; a failed `awb/read` call is a command problem the reviewer reports. Never substitute an unrestricted subagent or `awb/*`.
- In Claude Code, use a subagent type without edit tools, such as the built-in `Plan`, or a custom one whose `tools` are `Read`, `Grep`, `Glob`, and `Bash`; a skill's `allowed-tools` only pre-approves tools and restricts nothing. When the session has the awb MCP `read` tool, the reviewer runs `review-rules` and `review-receipt` through it, with Bash `python3 src/awb.py ...` as the fallback.
- In Codex, whose subagents inherit the session's sandbox and tools, start a fresh subagent all the same; the limit to read tools is then the brief's instruction alone.
- Only in a host with no subagents, follow **Brief** yourself, changing no file and running no command that writes until the report is complete, then act on it as **After the review** says. In `awb-package` that is a self-review by the agent that wrote the draft.

Bash in the Claude Code branch can still write, and Codex inherits tools, so those limits are conventions plus tool scoping where available. The Copilot custom agent has no shell or write tool.

## Brief

You review the package draft at `deliveries/<investigation>/<package>/draft/`. Its narratives are `findings.md`, `methodology.md`, and `methodology-note.md` when the draft holds it. Report findings; never fix them, and change no file. Run no command that writes: the only `awb.py` commands you run are `python3 src/awb.py review-rules check <investigation> <package>` and, for a scoped review, `python3 src/awb.py review-receipt show <investigation> <package>`, which write nothing (in Copilot, use the MCP calls in **Launch**), and where the host reads files only through a shell, read-only commands such as `cat`, `sed -n`, and `rg` are reads. Report every violation and narrative problem in this one pass, quoting each; the caller settles them all before the next review.

1. Run that command. Read `foundation/review-rules.md` when its `rules_file` is not `none recorded`, then the draft's narratives and the `revalidation_flags` in `manifest.json`.
2. Judge every rule the command lists that is not `retired`, against every narrative. A `matched` line is a candidate to judge, not a verdict; `no match`, `no pattern`, and `unchecked` rules are judged by reading. A rule's scope is what one violation covers: one line (`line`, the default), one slide (`slide`; in `methodology.md` and the note, one section under a `#`, `##`, or `###` heading), or one file (`document`); the command lists each match of a `slide` or `document` rule as that slide or file with the lines it matched, up to 20, and counts any more as `more_lines`, which you find by reading.
3. Check what no command checks: the narratives carry the same qualifications and caveats; no finding is worded more strongly than its claim strength, including wording off the `claims` check's list, such as a verb of change with an agent as its subject ("the carrier raised late orders"); every `represented_in` place of each `revalidation_flags` entry carries its caveat, or its omission when the disposition is `omit`; every claim in `findings.md`, with its numbers, traces to the matching claim in `methodology.md`, and `methodology-note.md` states nothing `methodology.md` does not support, since `check-draft` proves only that each number is recorded somewhere; and every sentence in any narrative that asserts that something was checked or verified, reconciles, sums or adds up to, or matches cites the recorded result or check that establishes it, covering all it asserts, such as every year rather than some: in `methodology.md` a result ID or evidence path, whose evidence you read to confirm; in `findings.md` and the note, the check in plain words, with its tolerance, that `methodology.md` cites. A sentence without one is a narrative problem. This pairs with the warning `awb.py state finding` gives on a finding whose wording asserts a reconciliation or a completed check that no passing check records.
4. Report exactly this, and nothing else, since the caller must account for every rule verdict and diagnostic before summarizing them in chat:
   - one line per rule in the command's order: `<ID> pass`, `<ID> retired`, or `<ID> violation <severity> <file>:<line> "<short quote>"`, with the rule's `error` or `warning`, one line per violation; a `slide` rule's violation is cited at its slide or section's heading line and a `document` rule's at its first offending line, quoting every offending line in it;
   - one line per step 3 problem: `narrative <file>:<line> "<short quote>" <what is wrong>`;
   - the command's `problems` and `errors` verbatim, or `command failed` with its output when it did not run; and
   - a last line, `review: clean` when there is no violation, no narrative problem, and the command exited 0, or otherwise `review: <v> violations (<e> error), <n> narrative problems, <c> command problems`, where command problems count the `problems` and `errors` entries, or 1 when the command failed.

When the caller gives you a prior report and a diff, or tells you to read them with `review-receipt show`, the review is scoped. Run the command as step 1 says, then judge steps 2 and 3 only on the diff's changed lines (for a `slide` or `document` rule, on each slide or file that holds one), the lines in the other narratives that state the same claims as a changed line, the places of each changed `revalidation_flags` entry, and each violation and narrative problem the prior report lists, confirming each is repaired; judge each rule added or changed since, as the diff of `foundation/review-rules.md` shows, against every narrative in full. When `diff_cut` is above 0, read each changed file in full. Report as step 4 says, with `<ID> pass` for each rule with no violation in that scope, and open the last line with `review (scoped):` instead of `review:`. When the prior report does not list a problem you find on a line the diff leaves unchanged, end its line with `(unchanged since the prior review)` and why the earlier pass missed it.

## After the review

Record every review as soon as it returns, before changing any file: run `review-receipt record <investigation> <package> --kind full|scoped --report -` through the `package` tool with the report as `stdin`, or `python3 src/awb.py review-receipt record ...` with it on standard input, adding `--accept "<file>:<line> <quote>: <the user's reason>"` once for each problem the user accepted. It keeps the report and a copy of what the review read; `review-receipt show` then reports the review `current` while it passed and nothing it read has changed, `failed` when it did not pass, and `stale`, with the diff since, once the narratives or `foundation/review-rules.md` change, or a `revalidation_flags` entry is added or removed or changes its finding, reason, `represented_in`, or whether its disposition is `omit`. A review is passed when its last line reports no `error` violation and no command problem, and the user accepted, with a reason, every `warning` violation and narrative problem it reports. A passed review completes a request or a release, full or scoped.

The first review of a draft, or any while `show` reports `none`, is full; every later one is scoped against the receipt, unless the user asks for a full one. A later review's repeat of an accepted problem is accepted again with its reason.

In `awb-package`, repair every `error` violation, every narrative problem, and every command problem, and repair a `warning` violation or report it for the user to accept. A command problem is an unavailable or failed `awb/read` call, remedied by registering the `awb` server or choosing the Local session target; a missing `findings.md` or `methodology.md`, or a narrative that cannot be read, repaired in the draft; or a malformed section of `foundation/review-rules.md`, repaired in place without changing any rule ID; ask the user when a broken rule's intent is unclear. Take a problem marked `(unchanged since the prior review)` to the user rather than repairing it. When a second review in one request still reports problems, stop repairing and start no third review in that request unless the user asks: show the user each problem in plain words with a recommended repair. Record those they accept, with their reasons, by recording that report again with `--accept`; after a repair they choose, the next review is scoped. `awb-release` repairs nothing and acts as its **2. Review** says.

When the user corrects a draft while reviewing it, decide whether later drafts could repeat the mistake. If they could, record the correction as a rule before repairing, so every later review checks it: `python3 src/awb.py review-rules add --area <area> --severity <error or warning> --rule "<what every draft must do>" --fix "<how to repair it>" [--pattern '<regex>'] [--scope slide|document]`. The area names what the rule governs, such as `periods` or `metric-definitions`; give a pattern when one line of text can show the violation, and a scope when one violation is a whole slide or file. Report the new ID. A correction that applies to this draft only, such as a preferred wording on one slide, is an edit, not a rule.
