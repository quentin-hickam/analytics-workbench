# Analytical implementation, validation, and evidence

Paths below that begin with `references/` or `assets/` are in the `awb-init` skill folder: `~/.claude/skills/awb-init/` (Claude Code) or `~/.agents/skills/awb-init/` (VS Code Copilot and Codex).

## Structure

Put reusable operations in `src/`: `src/preparation/` for acquisition, landing, conversion, session loading, normalization, and corrections; `src/exploration/` for neutral measurements, comparisons, profiles, and graph operations; `src/packaging/` for shared package assembly. Reuse existing operations first. Each investigation's `run.py` selects shared operations and its `settings.toml` supplies scope and settings. Intermediate computation stays in views and in-process results, never in CSV files handed between steps. An investigation without `run.py` gets one adapted from `assets/workbench/investigation/run.py` and `settings.toml` before its next rerun.

## Add a result

A new result is a `[results.<id>]` table in `settings.toml` holding the `question` it answers in the user's own words, never paraphrased; `answers = ["Q-NNN"]` when it answers ledger data questions; its `[results.<id>.validation]` table; and a query in `queries/<id>.sql`; adding one never edits `run.py`. Only a result that needs more than its query gets a producer module, `producers/<id>.py`, defining `produce(connection, sql, parameters)` as `run.py`'s comment describes. A result's evidence counts as code only `run.py`, its queries and producer, the investigation's shared SQL, `src/`, and the files its table lists in `code = ["helpers.py"]`, relative to the investigation: list there every other file its queries read directly or its producer imports or reads, such as a lookup CSV a query reads with `read_csv` or a helper module in the investigation folder, which a producer imports by name (`import helpers` for `helpers.py`), or a change to it leaves the result looking current, with or without a producer; a folder is refused, so list its files. Shared SQL, such as a screening filter several results apply, goes in the investigation's `views/*.sql`: result sessions load those files after the foundation views, in file-name order, and each counts as code for every result of the investigation. A file shared SQL reads directly, such as a lookup CSV, must be a publication or read by its own path and listed in every result's `code`, never through a glob or folder outside a publication; `run.py` exits 2, running nothing, otherwise, as `references/provenance.md` describes. A producer gets only the `[parameters]` its queries name as `$name` and those its table lists in `parameters = [...]`; reading another fails. Read `references/validation.md` only to write a validation spec beyond the keys the settings comments list, and `references/provenance.md` only to adapt `run.py`'s evidence recording or to port it.

A threshold, minimum, or exclusion the brief does not settle is the user's decision: propose it to the user before looking at which rows lead, and say so when you propose one after seeing results.

Specify four mechanical checks: required columns; plausible counts before and after each filter, with every filtered population reconciled by `reconcile()`, rows in equal to rows kept plus rows excluded by each rule, as `run.py`'s producer example shows; joins without unexpected multiplication, inspecting key uniqueness whenever counts change; and null rates for important fields. For a series summed over a period, also count the periods each entity in scope has data for, since a sum hides missing periods: a count below the period length is a caveat on the finding. Supply three judgments, each an outcome with a one-sentence detail: scope (explicit date filters and grouping dimensions), metrics (definitions, assumptions, and column meanings), and values (distinct values that drive business interpretation, inspected with `awb.py profile`).

Result queries use a stable total `ORDER BY`, with tie-breakers, so an unchanged result saves an identical table; result sessions run DuckDB on one thread, so floating-point sums repeat exactly. Save full precision in result queries and round only for display.

Before rerunning a supported or flagged finding, commit its evidence when README's `Commits:` line says `as I go`; otherwise suggest committing it, unless you already suggested a commit this session. While README's `Code history:` line says `none`, do neither. A result run before the project's first commit records `uncommitted` as its producing commit until it is rerun after that commit. Run results through the `awb` MCP `run` tool with the investigation and any result IDs, or with `python3 investigations/<name>/run.py [result-id ...]` when the host offers no MCP tools. It writes each row and prints one JSON line per result with the evidence path, `failed_checks`, `not_assessed`, and `state`: a new result gets a `provisional` placeholder; a rerun with unchanged table, checks, and settings keeps its row; any other makes it `provisional` unless superseded, logging a supported one in history. When a result declares `answers`, the run marks those ledger questions answered and lists them under `questions`; declaring or changing `answers` computes nothing and makes no result stale, and `awb.py questions answer Q-NNN --result <id>` links one already recorded. Validation is done when each `failed_checks` entry is understood and recorded, and each `not_assessed` entry is either supplied in settings or justified with a caveat. Word, promote, supersede, or caveat with `awb.py state finding <id>... --text --status --reason --caveat` in one call; `;` outside brackets separates `--caveat` notes. It warns, still writing, on a number the result does not record or "sums to" or "checked every" wording no passing check records: fix the number; state the check, with its tolerance, in the detail of a passing `values` or `metrics` judgment in `[results.<id>.validation]` and rerun; or reword. Before re-promoting, check the interpretation-driving values, which supported finding text includes, and the prior caveats in the rerun's history entry. Notes explain failed or not-assessed checks only for the checks they were written against: when a rerun changes those checks, promotion is refused until `--caveat` restates the notes that still hold.

Record a question the analysis raises, such as whether a dip is seasonal, with `awb.py questions add --origin analysis` and the question it serves as `--parent`. Status counts the roots, the questions with no parent, as the user's own, so only a question the user asks is a root.

## Claim strength

Each finding's Claim is the strongest wording it supports, and a new result starts at `association`. Set `descriptive` when the result only describes, such as a level, share, or trend: `awb.py state finding <id> --claim descriptive --reason "<why>"`. Correlations, group differences, and contrary groups from exploration or `run.py` stay `association` at most. Set `causal` only for a result whose design identifies the effect, naming that design: `--claim causal --basis "experiment: <design>"` or `--basis "natural experiment: <design>"`. A claim change writes history; a flagged finding's claim can only be lowered. `check-draft` refuses causal wording above a finding's claim.

## Rerun flagged findings

`awb-clean` makes shared corrections and flags the findings they affect. To rerun flagged findings on request, pass their result IDs, from each Evidence link, to `run.py`; it returns each to `provisional`, or `superseded` if it was, refreshes its check segments, keeps its notes, and moves the flag reason to `history.md`. If `run.py` cannot reproduce a flagged finding, write or extend its producer module first.
