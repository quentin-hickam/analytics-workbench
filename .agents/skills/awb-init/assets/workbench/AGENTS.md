# Analytics workbench

This repository contains one shared data foundation and multiple investigations. Keep source knowledge, quality records, vocabulary, the catalog, and canonical SQL views in `foundation/`. Keep reusable executable preparation, analytical operations, and package assembly in `src/`. Keep each question's scope, settings, exploration, findings, and history in `investigations/<name>/`.

## Start or resume work

- Resume the active investigation linked from `README.md` unless the user names another one, and briefly identify it. Point that link at `investigations/<name>/state.md` when an investigation is created or the user switches. Read its `brief.md` and `state.md`; consult `history.md` when prior reasoning matters. If a request could belong to more than one investigation, ask before changing their records.
- The same ask about a broader population that contains the current population is an expansion: it stays the same investigation and goes through `awb-init`, which revises the brief and asks only about the decisions the expansion reopens. Any other consequential scope change goes to the scoping interview. A related question about an independent population starts a new investigation with fresh state, history, and findings. Inherit the related investigation's method, settings, and package format as starting points, subject to the user's corrections; prior findings are context for method selection, not evidence about the new population.
- When the user asks where things stand or what they can do next, invoke `awb-status`.
- Invoke `awb-init` to establish or repair the workbench structure, to start or expand an investigation, or to resolve a consequential scope change. It owns the scoping interview and the investigation brief.

## Prepare and analyze data

- Let the active question bound preparation. Assess candidate sources only far enough to establish relevance and fitness, reading the landed copy, and record the assessment in `foundation/sources.md`. When a source is irrelevant, record why and stop there. Broader preparation requires an explicit request. Canonical data is not thereby fit for every question: check its coverage and recorded limitations against each investigation's scope.
- Land every acquisition durably with provenance before canonical ingestion, through `land()` in `src/preparation/landing.py`; source-specific code is only the `fetch` callable that writes the acquired files. Unless the project has its own layout, each acquisition is one directory `data/raw/<source>/<acquisition-id>/` holding the acquired artifacts byte for byte, every page or file of a multi-part acquisition, and `provenance.json`; `land()` writes it as `<acquisition-id>.partial/`, records checksums and the record counts the caller supplies, and renames it only when complete. A failed attempt keeps the suffix or is deleted, gets no Acquisitions row, and is noted in the source's row. A file the user hands over is an acquisition and is landed the same way. CSV and JSON are valid landed formats. Keep completed landed originals unchanged so conversion can be retried.
- `data/raw/` is excluded from Git, and a landed original often cannot be fetched again. Before landing the first acquisition, when the README's `Landed data is kept at` line is absent or reads `not yet recorded`, ask where landed originals are retained outside this checkout and record the answer on that line, adding the line directly after the README's `Active investigation` line when absent and preserving every other line. If the user declines, record `none chosen` and warn that landed data exists only in this checkout. A recorded `none chosen` is a decision: repeat the warning after each landing and record a location whenever the user names one.
- After each completed landing, when the recorded location is a filesystem path reachable from here, run `retain()` from `src/preparation/landing.py`, which copies the acquisition directory to `<location>/data/raw/<source>/<acquisition-id>/` without overwriting and reports any conflict and any file-list or checksum discrepancy; report a conflict to the user. Otherwise state exactly what to copy and where. Record the retained copy in the acquisition's row in `foundation/sources.md`: the destination path once `retain()` reports no discrepancies, or `this checkout only` until a copy is verified or the user confirms making it. When the user records or changes the location, run `retain()` for every acquisition whose retained copy is missing.
- Publish by converting landed originals into validated Parquet in `data/parquet/`, then exposing canonical DuckDB views. Unless the project has its own layout, publish through `publish()` in `src/preparation/landing.py`: it writes conversion output to `data/parquet/<dataset>/<publication-id>.partial/`, runs the supplied validation, writes `publication.json` with the cited acquisitions' checksums copied from their `provenance.json` and the conversion commit, and renames the directory beside the publications readers are using rather than over them. Each view names the publication it reads, and the catalog records it, so switching a view to a newer publication is a deliberate preparation change. Remove a superseded publication only when no reader needs it. Each analytical process opens its own DuckDB session with `session()` from the same module, which loads every `foundation/views/*.sql` in name order, so a view file sorts after the views it reads.
- Preparation owns reusable parsing, normalization, checks, and documented corrections; record limitations and correction rationale in `foundation/quality.md`. EDA consumes canonical data. Keep exploratory transformations in `investigations/<name>/exploration/` until a generally valid rule is deliberately promoted through preparation. A query run a second time is saved as `investigations/<name>/exploration/<topic>.sql`, or promoted to a view in `foundation/views/` when generally valid, and rerun by path through `session()` from `src/preparation/landing.py`, never retyped. Profile a view or result with `profile()` from `src/exploration/validate.py` rather than ad hoc counting queries. Population choices, periods, filters, exclusions, and assumptions stay local to the investigation. Exploration need not wait for cleaning to finish; preparation and EDA iterate as issues surface.
- Keep intermediate computation in canonical views and in-process results. Use `data/cache/` only for expensive, rebuildable results, each described in `foundation/catalog.md`. Audience-facing dataset exports selected for a delivery package are separate from intermediate computation. Parquet conversion is a storage boundary, not a place to materialize each transformation; documented normalization and corrections may stay in views. Do not accumulate materialized tables in a persistent DuckDB file, except as a deliberate cache recorded in the catalog; that has caused runaway storage growth.
- When a different backend is justified, preserve independent source landing and the preparation/EDA boundary. Add versioning, invalidation, or pipeline machinery only for a concrete project need.

## Write analytical code

- Put acquisition, landing, conversion, session-loading, and reusable normalization and correction code in `src/preparation/`, starting from `landing.py`, copied from the `awb-init` skill's `assets/awb_landing.py` the first time data is landed or a session is opened and imported from there, never from the skill folder; neutral measurements, comparisons, profiles, and graph operations in `src/exploration/`; shared package assembly in `src/packaging/`; and shared figure style and figure builders in `src/presentation/`. An investigation composes those operations through a thin layer of scope, settings, and selected operations in `investigations/<name>/`: one named settings file in the project's configuration format (`settings.toml` when the project has no convention) and the investigation's own copy of the composition entry, runnable as a script.
- Invoke `awb-visualize` whenever a chart, figure, diagram, or formatted results table is produced; figure code is presentation and stays out of neutral operations.
- Group meaningful variation in named configuration with sensible defaults, and give distinct workflows distinct entry points. Reuse existing operations before adding new ones. A CLI is optional; an entry point exposes only the few controls its task needs and leaves the rest to configuration. The investigation's composition entry, run with its settings file, is the only producer of a finding: every result that enters `state.md` was produced or reproduced by running it. Computation done ad hoc in chat is exploration, not a finding, until the entry produces it.
- Compute before interpreting. A conclusion read first becomes what the analysis looks for: it frames the questions and makes agreement look like confirmation. Apart from a related investigation's findings used as context for method selection, do not read other investigations' or projects' conclusions on your own initiative before this investigation's own results exist. Preserve relevant results that challenge the expected explanation, and keep presentation logic out of neutral operations.
- Validate before presenting any result or recording it as a finding, and record the checks with its evidence. The first time a result needs validation, copy `awb_validate.py` from the `awb-init` skill's assets to `src/exploration/validate.py` and import it from there, never from the skill folder; a project that does not use Python ports the same interface and record. Four checks are mechanical and run through `validate(frame, spec)`: columns (required fields exist); row counts (counts before and after each filter are plausible); joins (no unexpected row multiplication, and key uniqueness inspected whenever counts change); nulls (missing-value rates for important fields). `profile(frame)` gives the counts, null rates, and distinct values to inspect. Three are judgment checks, passed to `validate()` as an outcome and a one-sentence detail so they land in the same list: scope (date filters and grouping dimensions are explicit); metrics (definitions, assumptions, and the meaning of the columns used are documented); values (distinct values inspected when they drive business interpretation). A judgment check left out is recorded as not assessed, which is not a pass. Record the returned list unchanged with the result's evidence. A result that fails a check is not a finding until the cause is understood and recorded.
- Track all analytical code in Git. Record each result's evidence with `record_evidence` from `src/provenance.py`, copied from the `awb-init` skill's `assets/awb_provenance.py` the first time a result needs it and imported from `src/` thereafter, never from the skill folder. It writes `investigations/<name>/evidence/<result-id>.json`: the producing commit, each uncommitted producing path with its checksum, the input publications and acquisitions with the checksums their publication and provenance files record, the view definitions read with their checksums, the resolved settings, and the validation checks performed, with unknown provenance named as unknown with its reason, so packaging can distinguish the producing state from a later checkout. Before any commit exists it records `uncommitted` with the checksums of the producing files; suggest a commit so later results carry a SHA. A project that does not use Python ports the helper's interface and keeps its file format.
- Anything the workbench does more than once is code, not a procedure to repeat by hand. Landing, publication, retention copies, result evidence, validation checks, session loading, manifest inventory, and state comparison each have one helper in `src/`, written or copied the first time the need arises and called thereafter. Save a query or check run a second time to a file and rerun it by path. Regenerate a helper only to change its behavior.

## Maintain meaning and records

- Challenge ambiguous business and analytical terms, test proposed definitions with concrete cases, and compare them with source data and analytical logic. Record resolved shared meanings immediately in `foundation/glossary.md`, a brief explained local departure in the investigation's `brief.md`, population and period choices as settings, and dataset, view, and cache descriptions in `foundation/catalog.md`. These records replace `CONTEXT.md`, `CONTEXT-MAP.md`, and ADRs.
- Update `state.md` whenever current findings, unresolved issues, revalidation flags, or next steps change. Append to `history.md` whenever a meaningful finding, analytical decision, caveat, superseded conclusion, or relevant source limitation changes; its header defines what belongs there and what stays in Git history. Write an explicit checkpoint when the user requests one before switching investigations. When the user says who will read the delivered documents, record it in the Audience section of the investigation's `brief.md`.
- When EDA reveals a shared data issue, assess the candidate correction locally. Once accepted as general, implement it through preparation, document it in the foundation, and flag every finding it may affect for revalidation with a reason, keeping its prior status visible. Affected analyses are rerun and conclusions revised only on request. A rerun is one command: run the investigation's composition entry with its settings file, then record each result's evidence with `record_evidence()` from `src/provenance.py`; nothing is rebuilt in chat. When the entry cannot reproduce a flagged finding, extend the entry first. Prior numbered releases stay unchanged.

## Package only on request

- Create or refresh a delivery package only when the user explicitly asks, by invoking `awb-package`. A numbered release happens only when the user explicitly marks a package delivered, by invoking `awb-release`. Automatic record maintenance never triggers packaging or another ad hoc deliverable.
