# Repair and upgrade

1. Run the installer with `--upgrade`. The user's request authorizes it: it installs missing helpers, guides, and the `foundation/references/` README and replaces only `earlier` copies (unmodified older copies that its receipt recorded) of helpers, package formats, workbench guides, and that README. It records what it writes in the project's `.awb-receipt.json`.

   ```sh
   python3 <skill-directory>/scripts/install_helpers.py <project-root> --upgrade
   ```

   Run it with README's `Project interpreter` when the line names one; the installer refuses another interpreter, and writes the line when it is missing.

2. When it reports `customized` files or `retired` files, ask the user once about all of them: show each customized file's difference (`git diff --no-index <project file> <asset>`, the asset from `customized`) and ask whether to replace, keep, or merge it; ask whether to remove the unmodified retired files. A customized retired helper under `src/` is no longer imported: show its history and uncommitted changes (`git log -p --follow -- <file>` and `git diff -- <file>`) and ask whether to port its changes into the current helper or remove it. Then rerun the installer with `--upgrade`, a `--replace <path>` for each file to replace, and `--remove-retired` if agreed. Make hand merges and ports with ordinary edits, keeping the project's changes, and delete each ported helper. Other customized retired files are the project's own; keep and report them.
3. Reconcile `AGENTS.md` and `README.md` with the [agent instructions](../assets/workbench/AGENTS.md) and [orientation](../assets/workbench/README.md) templates: add what the template holds and the project lacks, such as routing to every skill, command conventions, and **Asking for things** requests; delete lines naming workbench skills, commands, or paths the template no longer has; keep project-specific content. List every [ignore rule](../assets/workbench/.gitignore) the project's `.gitignore` lacks and ask the user once, naming them all, whether to add each: a missing rule may be one the project dropped on purpose. Add each rule the user accepts; each rule the user declines stays dropped, and report it as an exception. Place each negation such as `!.env.example` after every rule it overrides, moving an existing one that sits earlier, then run `git check-ignore --no-index .env.example .env .env.local`. Its output must agree with each of these rules the project keeps: it prints `.env` if the `.env` rule is kept, prints `.env.local` if the `.env.*` rule is kept, and omits `.env.example` if the `!.env.example` rule is kept.
4. Reconcile each investigation's `run.py` with the [template](../assets/workbench/investigation/run.py) (`git diff --no-index`): take the template's changes and keep the investigation's other adaptations. Move each producer an older `run.py` registers in a `PRODUCERS` dict into `producers/<result-id>.py`, renamed `produce`, with the helpers it calls, and add to that result's settings table each other file it imports or reads, as `code = [...]`, and each `[parameters]` entry it reads that no query names, as `parameters = [...]`. Add as well, for every result, each file its queries read directly, such as a lookup CSV in `read_csv`: it counted before only because every file in the investigation folder did. Then rerun those results: the move changes their producing code.

Repair is done when the last installer output shows every file `installed`, `current`, `replaced`, or kept or merged by the user's choice, every retired file `removed` or kept by choice, each customized retired helper is ported or removed, each `run.py` matches its template apart from the investigation's adaptations, both root files match their templates apart from project content, `.gitignore` holds every template rule apart from those the user chose to keep dropped, each reported as an exception, and step 3's `git check-ignore` output agrees with each `.env` rule the project keeps.

Report also each investigation without `run.py`, which gets one before its next rerun, and each without `questions.json`, whose Material unknowns and question-shaped Next steps `awb-scope` moves into a new question ledger when it next runs on it. Repair leaves investigation records as they are.
