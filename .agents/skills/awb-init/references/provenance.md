# Result evidence helper

Call the project copy at `src/provenance.py`; its module docstring holds the full `awb-evidence/3` schema.

## The findings row

A result that raises prints `{"result_id", "error"}` with the traceback on stderr, the other results still run, and `run.py` exits 1. Before it unlinks the evidence, `run.py` calls `prior_result()`, which captures the `evidence_commit()` citation and, as the baseline, the saved table's sha256 with the evidence's checks and scoped settings. After `record_evidence()`, `record_finding()` writes the result's one row and `run.py` prints `state`: `added` (a `provisional` placeholder row), `kept` (baseline unchanged, nothing written), `refreshed`, or `flag cleared`. A refreshed row becomes `provisional` unless superseded and gets a history entry when it was supported; a flagged row returns to `superseded` or `provisional`, keeping its notes and dropping its flag reason, which the history entry records. Each entry's `notes_checks` records the checks caveat its notes were written against, and `state finding` counts the notes as explaining failed or not-assessed checks only while it equals the current one. The caveat's `failed checks:` and `not assessed:` segments are reserved for the writer; other segments are notes from `awb.py state finding --caveat`, which splits its text into notes at each `;` outside parentheses and square brackets: `)` or `]` closes the innermost open bracket, so a half-open interval such as `[0, 1)` closes; a closer with no bracket open, as in `1) first; 2) second`, is text, and so is a bracket that never closes, unless a `;` follows it, which is refused. With `--text`, or a promotion to `supported`, `state finding` warns, never refuses, on each number in the finding that its result's table, profile, checks, and settings do not record, read by the number reader `check-draft` uses, in `src/packaging/draft.py`, which it loads only then and skips when that file is absent; and on wording that asserts a reconciliation or a completed check, matched as whole words in any case (sum, sums, summed, or summing to; add, adds, added, or adding up to; reconcile, reconciles, reconciled, reconciling, or reconciliation; checked or verified every, each, or all), when no passing check's name or detail uses wording of the same kind: sum wording backs only a sum, reconciliation wording only a reconciliation, and checked or verified wording only a completed check, so a scope judgment "Checked all date filters are explicit" never backs "sums to", nor does the `reconciled:` detail of a `reconcile()` row count. To record the check, state it, with its tolerance, in the detail of a passing `values` or `metrics` judgment in `[results.<id>.validation]` and rerun; otherwise reword. Evidence it cannot read gives one warning that nothing was checked. The warnings print before the rows. `findings.json` (`awb-findings/1`) owns all five cells, the Claim cell from each entry's `claim` and `claim_basis` (`descriptive`, `association`, or `causal` with a basis beginning `experiment: ` or `natural experiment: `, required, never defaulted when absent); a new row starts at `association` and a rerun keeps its claim; without the file the table renders empty, so a row written by hand is drift. Writers refuse table drift, and `prior_result()` refuses it before a rerun removes evidence. `python3 src/awb.py state render --investigation <name>` restores the JSON table and prints discarded rows; re-apply intended edits with `state finding`, or flags with `state flag` (a JSON list of `result` and `reason` on stdin; `--check` validates without writing). Only table rows are rendered, and a row cut off below the table still counts as drift; `state issues` and `state next` never touch the table. All temporary files are written first, then findings, state, and history are replaced in order with signals deferred. New evidence is removed only if findings.json was not replaced. A failed state replacement names `state render`; a failed history replacement names its missing prior rows. A kill or power loss between replacements can still leave the table behind findings.json, which `state render` restores, or lose the history entry, risks accepted over a recovery mechanism. `finding_row()` returns the row without writing it, keeping an existing row's Finding and Claim cells.

The saved table under `results/` holds the computed values packaging later serializes. `results/` is output, not producing code. `run.py` deletes a result's evidence before rewriting its table, so a run that fails partway leaves no evidence rather than evidence for another table.

## Adapt what a result records

`run.py` records each result through `record_evidence()`. Set `views = [...]` in a result's settings when its producer reads views its queries do not name (detection errs toward recording a view); it replaces detection from the queries, while the investigation's `views/*.sql` files, and the foundation views they read, are recorded as views for every result whatever it says, so the publications they read are compared too. Each `views` entry is a project-relative `.sql` file directly under `foundation/views/` or the investigation's `views/`, which `result_problems()` checks, so `run.py` exits 2 naming any other entry before it runs anything. `run.py` opens one `session(root, investigation=<name>)`, which loads the investigation's `views/*.sql` after the foundation views and runs DuckDB on one thread, so a rerun repeats floating-point sums exactly. Producing code is an allow list: `run.py`; the result's own `queries`; its producer module, `producers/<result-id>.py`, listed whether or not it exists, so writing one stales the result; the files its table lists in `code = [...]`, relative to the investigation, each an existing file in the project, never a directory, since a file added to a directory later would not count; the investigation's `views/*.sql` (`investigation_views()`), for every result, a file added there later included; and `src/` except `awb.py`, `provenance.py`, and `packaging/`, which only dispatch, record, or package. Nothing else counts: notes, prose such as a `methodology.md`, other results' queries and producers, and any file the result's queries read directly, or a producer or an adapted `run.py` imports or reads, that the result's table does not declare. Declare every such file, such as a lookup CSV a query reads with `read_csv`, a helper module in the investigation folder, or exploration SQL a producer reads, or a change to it leaves the result looking current, with or without a producer module. A file the investigation's `views/*.sql` reads directly is code for every result, so it must be a publication, read through a path naming `data/parquet/<dataset>/<publication>/`, or listed in every result's `code`. `run.py`'s `unrecorded_reads()` checks each string literal in those files, outside comments, that names files in the project, a glob included, and exits 2, running nothing, naming the file and each result run whose `code` lacks it, or naming a file outside the project, which no `code` can list; a path built at run time, or one naming a directory, is not checked. A change to `src/` stales every result; finer tracking, such as following imports, is left out. Pass `code_paths=[...]` in `run.py`'s `record_evidence` call to add producing code relative to the project. Unknown provenance is recorded as `{"unknown": reason}`.

`run.py` loads a result's producer module by its result ID, `producer_path()`, so adding a result never edits `run.py`. The file name is the ID exactly; an ID is a letter or digit followed by letters, digits, `.`, `_`, or `-`, and `result_problems()` refuses any other, so `run.py` exits 2 before it runs anything. The module defines `produce(connection, sql, parameters)`, receiving the session, the texts of the result's queries in order, and the parameters it reads, and returns `(frame, measured)`; `run.py` binds its `run()` in the module before loading it, and a result without a module gets its first query's output. An older `run.py` whose `PRODUCERS` dict holds producers is reconciled as [repair](repair.md) step 4 says.

Settings are recorded per result: `record_evidence()` refuses a settings file without the result's `[results.<id>]` table, and the evidence keeps only that table and the `[parameters]` entries the result reads, compared by content alone. A result reads each parameter its queries name as `$name`, anywhere in their text, comments included, and each its table lists in `parameters = [...]`, for a parameter only its producer reads. `run.py` passes a producer only those (`result_parameters()`), so reading another raises `KeyError`, through `get()` too, rather than escaping the comparison, and passes the same mapping to `record_evidence(parameters=...)`. A name the result reads that `[parameters]` does not set raises `KeyError` with `[]`, and `get()` gives its default. A query names a parameter with letters, digits, and `_` only, so a name holding `-`, as a TOML bare key may, reaches only a producer whose table lists it. Called without it, as an older `run.py` whose producers receive every entry calls it, `record_evidence()` records every entry. The table needs `question`, one line in the user's words, and may list `inputs`, the dataset or view names the producer reads; the evidence copies both verbatim, and `result_problems()` names what a table lacks. `run.py` checks every wanted result first and exits 2, running nothing, when one lacks its question; `awb.py state` shows each finding's question beside its result ID. Adding or editing another result's table, a parameter it does not read, or another top-level table such as `[eda]`, leaves the result current, while a change to a parameter it reads or to its own table fails the `settings` comparison. The exception is the table's optional `answers`, a list of question ledger IDs: `record_evidence()` refuses an ID `questions.json` lacks or whose answerer is not `data`, and `run.py` exits 2 on either before it runs anything, since a rerun replaces the prior evidence first; `record_finding()` marks those questions answered and returns `questions` (`answered`, `linked`, `skipped`, or an `error` naming `awb.py questions answer --result`), and every settings comparison, the exact-rerun baseline included, leaves `answers` out. Declared `code` is checked the same way: `run.py` exits 2, running nothing, when a path is missing, a directory, or outside the project, and `record_evidence()` refuses it too. The `settings` comparison reads the parameters the evidence recorded and those the result reads now, so a parameter it starts to read counts at once, and evidence that recorded every entry compares on each until its result is rerun. A rerun's exact-match baseline compares only the parameters that run recorded, so an unchanged result keeps its row. Keep anything a result reads in `[parameters]` or its own table.

## Question tree

`questions.json` records a question's `parent` as an existing question ID or an empty string for a root, and `priority` as `must`, `should`, or `could`, defaulting to `should`. `awb.py questions add` and `questions edit` accept `--parent` and `--priority`; an empty `--parent` makes a root, which is kept for a question the user asked, since status counts the roots as the user's questions. Missing parents and cycles are refused. `questions list` and `questions.md` walk the tree depth-first, with roots and each parent's children sorted by priority, then ID number (`Q-999` before `Q-1000`), and children indented. A filtered `questions list` indents a question only under ancestors it also lists. The list includes answerer, kind, priority, and parent (`root` for an empty parent).

An answered data question displays `answered (awaiting recheck)` when any answering finding is flagged (`revalidation-needed`) or superseded, including when another answering finding remains settled. This is derived from the current findings; the question's stored status stays `answered`. The status collector uses this display status in its counts and lists those questions under `awaiting_recheck`.

Finding writes refresh `questions.md` in the same prepared write batch, after state and before history, while preserving `questions.json`. They refuse hand edits to the question view. If replacement is interrupted after findings changed, restore the question view with `questions render` before another finding write.

## Evidence comparison

`awb-package`'s `export` command and `python3 src/awb.py stale`, run `compare_evidence(root, evidence_path)`: five comparisons in order (`committed-code`, `uncommitted-code`, `views`, `inputs`, `settings`), each `{name, paths, outcome, detail}`. It compares state; it does not revalidate. It reads only `awb-evidence/3` files whose settings name their result; any other evidence fails all five comparisons, so rerun its result.

Evidence also records the `runtime`: Python version, platform, and the installed versions of `duckdb`, `pandas`, and each package `requirements.txt` names, directly or through a `-r` include, and under `unread_requirements` each requirements line or include the helper's `read_requirements()` could not read (its docstring gives the rules). `stale` compares it with the interpreter running `stale` and lists differences and unread lines under `runtime_mismatches`, apart from `results`: a warning that asks for a rerun decision, never a stale result. `src/awb.py` runs `stale` under README's `Project interpreter`, so run `run.py` with it too. Pin versions in `requirements.txt` to keep reruns on the recorded runtime, and name the package of an unread line, as with `#egg=NAME` or `NAME @ REFERENCE`, to record its version.
