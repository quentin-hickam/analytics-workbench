# Result evidence helper

Call the project copy at `src/provenance.py`; its module docstring holds the full `awb-evidence/3` schema.

## The findings row

A result that raises prints `{"result_id", "error"}` with the traceback on stderr, the other results still run, and `run.py` exits 1. Before it unlinks the evidence, `run.py` calls `prior_result()`, which captures the `evidence_commit()` citation and, as the baseline, the saved table's sha256 with the evidence's checks and scoped settings. After `record_evidence()`, `record_finding()` writes the result's one row and `run.py` prints `state`: `added` (a `provisional` placeholder row), `kept` (baseline unchanged, nothing written), `refreshed`, or `flag cleared`. A refreshed row becomes `provisional` unless superseded and gets a history entry when it was supported; a flagged row returns to `superseded` or `provisional`, keeping its notes and dropping its flag reason, which the history entry records. Each entry's `notes_checks` records the checks caveat its notes were written against, and `state finding` counts the notes as explaining failed or not-assessed checks only while it equals the current one. The caveat's `failed checks:` and `not assessed:` segments are reserved for the writer; other segments are notes from `awb.py state finding --caveat`. `findings.json` (`awb-findings/1`) owns all five cells, the Claim cell from each entry's `claim` and `claim_basis` (`descriptive`, `association`, or `causal` with a basis beginning `experiment: ` or `natural experiment: `, required, never defaulted when absent); a new row starts at `association` and a rerun keeps its claim; without the file the table renders empty, so a row written by hand is drift. Writers refuse table drift, and `prior_result()` refuses it before a rerun removes evidence. `python3 src/awb.py state render --investigation <name>` restores the JSON table and prints discarded rows; re-apply intended edits with `state finding`, or flags with `state flag` (a JSON list of `result` and `reason` on stdin; `--check` validates without writing). Only table rows are rendered, and a row cut off below the table still counts as drift; `state issues` and `state next` never touch the table. All temporary files are written first, then findings, state, and history are replaced in order with signals deferred. New evidence is removed only if findings.json was not replaced. A failed state replacement names `state render`; a failed history replacement names its missing prior rows. A kill or power loss between replacements can still leave the table behind findings.json, which `state render` restores, or lose the history entry, risks accepted over a recovery mechanism. `finding_row()` returns the row without writing it, keeping an existing row's Finding and Claim cells.

The saved table under `results/` holds the computed values packaging later serializes. `results/` is output, not producing code. `run.py` deletes a result's evidence before rewriting its table, so a run that fails partway leaves no evidence rather than evidence for another table.

## Adapt what a result records

`run.py` records each result through `record_evidence()`. Set `views = [...]` in a result's settings when its producer reads views its queries do not name (detection errs toward recording a view). Producing code is `run.py`, the result's own `queries`, the investigation's other code, and `src/` except `awb.py`, `provenance.py`, and `packaging/`, which only dispatch, record, or package; another result's queries never make it stale. Pass `code_paths=[...]` in `run.py`'s `record_evidence` call to add producing code outside those, such as exploration SQL a producer reads. Unknown provenance is recorded as `{"unknown": reason}`.

Settings are recorded per result: `record_evidence()` refuses a settings file without the result's `[results.<id>]` table, and the evidence keeps only `[parameters]` and that table, compared by content alone. The table needs `question`, one line in the user's words, and may list `inputs`, the dataset or view names the producer reads; the evidence copies both verbatim, and `result_problems()` names what a table lacks. `run.py` checks every wanted result first and exits 2, running nothing, when one lacks its question; `awb.py state` shows each finding's question beside its result ID. Adding or editing another result's table, or another top-level table such as `[eda]`, leaves the result current, while a change to `[parameters]` or its own table fails the `settings` comparison. The exception is the table's optional `answers`, a list of question ledger IDs: `record_evidence()` refuses an ID `questions.json` lacks or whose answerer is not `data`, and `run.py` exits 2 on either before it runs anything, since a rerun replaces the prior evidence first; `record_finding()` marks those questions answered and returns `questions` (`answered`, `linked`, `skipped`, or an `error` naming `awb.py questions answer --result`), and every settings comparison, the exact-rerun baseline included, leaves `answers` out. Keep anything a result reads in `[parameters]` or its own table.

## Evidence comparison

`awb-package`'s `export` command and `python3 src/awb.py stale`, run `compare_evidence(root, evidence_path)`: five comparisons in order (`committed-code`, `uncommitted-code`, `views`, `inputs`, `settings`), each `{name, paths, outcome, detail}`. It compares state; it does not revalidate. It reads only `awb-evidence/3` files whose settings name their result; any other evidence fails all five comparisons, so rerun its result.

Evidence also records the `runtime`: Python version, platform, and the installed versions of `duckdb`, `pandas`, and each package `requirements.txt` names, directly or through a `-r` include, and under `unread_requirements` each requirements line or include the helper's `read_requirements()` could not read (its docstring gives the rules). `stale` compares it with the interpreter running `stale` and lists differences and unread lines under `runtime_mismatches`, apart from `results`: a warning that asks for a rerun decision, never a stale result, so run `stale` with the interpreter that runs `run.py`. Pin versions in `requirements.txt` to keep reruns on the recorded runtime, and name the package of an unread line, as with `#egg=NAME` or `NAME @ REFERENCE`, to record its version.
