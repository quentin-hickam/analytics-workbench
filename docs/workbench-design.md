# Workbench design decisions

These notes capture accepted decisions from the design interview. The workflow design remains in progress.

## Baseline principles

- Prefer readable, reusable, modular code. Organize code around cohesive responsibilities, with small, explicit interfaces between data preparation, analytical methods, and packaging.
- Parameterize meaningful variation across populations or iterations while keeping each module's interface focused. Group related settings into named configuration objects or files, with sensible defaults. Expose only the small set of controls needed for the task at the entry point; a CLI is optional, not the goal. When options represent distinct workflows, separate those workflows into modules or entry points rather than expanding one universal command. Share common logic instead of duplicating scripts.
- Maintain a consistent directory structure across projects and investigations. The current workflow uses root-level `src/` and `data/`; the expanded layout is still to be specified.
- Do not export intermediate CSV files as handoffs between analysis steps. Keep intermediate computation in views or the analytical runtime; cache expensive results deliberately. User-selected dataset exports for delivery packages are separate from intermediate computation.
- Maintain canonical, reusable views of the data in the shared analytical store. DuckDB currently serves this role, but the principle survives a change in storage technology.
- Maintain a catalog of the shared analytical store's datasets and canonical views, separate from investigation records. Its exact format remains to be specified.
- Validate before presenting results: columns, row counts, joins, nulls, scope, metrics, and values. This checklist is carried from the earlier framework as an always-on requirement recorded with each result's evidence.
- Generate ad hoc deliverables only upon explicit user invocation.
- Track all analytical code in Git and identify the producing commit in the package manifest.

## Project and investigation boundaries

A project contains a shared data foundation and multiple investigations, each with its own business question, progress, and findings. Data preparation and quality knowledge belong to the shared foundation.

The user's example distinguishes an initial communications analysis of approximately 120 employees, an expansion to approximately 900 employees within the same investigation, and a separate investigation asking the same questions about an independent group. A general rule for investigation boundaries remains to be defined.

When starting a related investigation, assume the current analytical method and parameters apply unless the user corrects them. Carry those choices forward as the starting configuration, reuse shared preparation logic and analysis code, and begin fresh findings and progress for the new scope. Prior findings are not evidence for the new population.

## Storage and computation

Data preparation is driven by the active business question. Assess candidate sources for relevance and fitness first, doing only enough cleaning to make that assessment. Prepare the data needed for the question; broader preparation requires an explicit request. If a source proves irrelevant, record why and stop preparing it.

An investigation motivates preparation, while reusable cleaning and normalization logic and discoveries about data quality belong in the shared foundation. Question-specific filters, exclusions, and analytical assumptions belong to the investigation. Preparation and analysis can proceed iteratively as new issues are discovered.

The default storage workflow is independently landed source files, validated Parquet datasets, and canonical DuckDB views over those files. Each analytical process owns its DuckDB session and loads shared, Git-managed SQL definitions. A shared writable DuckDB file is not required. Projects with different needs, including incremental workloads, may use a different backend while preserving the ingestion boundary below.

Data gathering must always land source records durably and independently before introducing them into the canonical database. API responses and SQL Server extracts are captured as source artifacts with acquisition provenance, rather than being streamed directly into canonical tables as their only retained representation. Completed landed artifacts are the inputs to conversion and preparation; incomplete acquisitions remain unpublished. Preparation can be retried from those artifacts without fetching the source again.

Preserve landed originals separately from derived Parquet datasets. Conversion establishes a validated storage representation, not an automatic claim that cleaning is complete. Canonical views apply documented normalization and correction rules. Initial CSV/JSON landing is source acquisition and does not violate the prohibition on intermediate CSV handoffs. The same independent-landing boundary applies to each batch of an incremental project.

`data/raw/` is excluded from Git, like `deliveries/`, and for the same reason the project records where copies are kept. Parquet datasets and caches can be rebuilt from landed originals and Git-managed code, but a landed original often cannot be fetched again: a point-in-time API response or an extract from a system that has since changed is lost with the one disk that holds it, and every release manifest citing that acquisition then points at nothing. The project README therefore records where landed data is kept, the agent copies each completed landing there when the location is reachable and otherwise says what to copy, and the source register records each acquisition's retained copy so status and release can report what exists only in this checkout. The project AGENTS.md requires the data guide before acquisition or storage changes; that conditional guide holds the retention procedure. It retains landed originals outside the checkout; it does not add inputs to releases, which remains the explicit exact-rerun choice.

Prefer views; cache results when recomputation is expensive. Accumulating materialized tables within one database has caused excessive storage growth.

## Preparation and exploration boundary

Preparation owns explicit, reusable normalization, quality checks, and documented corrections that produce canonical data. EDA consumes canonical data and may apply local exploratory transformations; it does not silently rewrite canonical data or shared preparation rules. Promote an exploratory transformation into shared preparation deliberately, keeping question-specific exclusions local. This boundary does not require cleaning to finish before exploration, separate databases, or a heavyweight pipeline.

Shared analytical code implements neutral operations on data independently of a desired narrative or conclusion. Investigations compose those operations through a thin run script, `run.py`, over their scope and settings; interpretation and presentation remain separate from computation. Reuse existing operations where possible, return relevant results even when they contradict an anticipated explanation, and avoid speculative general-purpose frameworks.

## Working data and release history

Working analysis uses current data and definitions, refreshing caches as needed. Each release is frozen: it retains its exact exported results and records its Git commit SHA, input provenance, analytical parameters, and the runtime of each represented result, so later workbench changes cannot alter what an earlier release represents.

Preserving enough data for exact reruns is an explicit choice, rather than a default full database snapshot for every release. Code is tracked in Git; delivery packages currently are not.

## Package revisions

Creating or refreshing a delivery package requires an explicit user request. Automatic maintenance of investigation records does not trigger package generation or revision.

When creating a package, ask the user which datasets to include. Reuse that selection for revisions unless the user changes it or the selected datasets no longer fit the scope; ask again when they no longer fit. Do not assume a default set of dataset exports for a new package.

Draft packages may include flagged findings, with a clear caveat beside each affected conclusion and a short list of unresolved issues. Before marking the package delivered, require the user's disposition for each: revalidation, omission of the affected conclusion, or explicit release with the caveat. Packaging does not automatically trigger analysis reruns.

Each package has one stable name and one current working draft. Revisions update that draft until the user explicitly marks it as delivered. That milestone preserves a numbered, frozen release; subsequent edits begin the next working revision. Numbered releases are created only at explicit delivery milestones. A revision requested with the milestone is shown to the user before the release, unless they say to release without seeing it, because one was once frozen before the user saw it.

An investigation has one delivery package by default. Its draft holds an audience-facing findings document, written as the deck outline whose **Answer** slide is the executive summary, an internal methodology reference, and, when the audience needs one, an audience-facing methodology note. Additional packages are created only for an independent scope or delivery schedule.

Package structure is a shared format choice, not an investigation choice. Related investigations inherit the findings, methodology, deck rule, and assembly conventions; their narrative and results are specific to the investigation.

Each release's findings document is self-contained for the audience recorded in the investigation brief and is the only source of slide content. It is written in that audience's business terms: file names, view and column names, settings keys, internal identifiers, and code terms stay out, and a packaging helper checks for them. The methodology document is self-contained as the account of the analysis and is where those identifiers belong; it lets the deck builder and analysts look up the internal logic behind a decision. The two agree in claims, numbers, qualifications, and caveats, and each finding has a section under the same heading in both. The packaging helper also checks that every number in either traces to a value a represented result records, within rounding, or is listed with its reason in the manifest; a methodology **Claim strength:** line that the claim check accepts repeats the claim strength its results record, design basis included, so its numbers are not read. `awb.py state finding` reads a finding's text with the same reader when the finding is worded or promoted, and warns on each number its result does not record and on wording that asserts a reconciliation or a completed check that no recorded check backs, so the gap shows when the finding is written rather than first at packaging. It warns and never refuses, because the packaging check still refuses and an early refusal would only block rewording; it loads the reader from the project's packaging helper on demand, so provenance still runs without it. When applicable, both include a brief section describing changes since the previous release.

The methodology reference is internal and long, and audiences asked for a methods note they could read; the notes agents wrote outside the package escaped every check. The optional methodology note is therefore part of the draft: a short account of method, sources, definitions, exclusions, and limitations under the findings translation rule, delivered beside the deck like datasets. The names, numbers, claims, and Markdown checks and the review rules read it, and it is held to the strongest represented claim strength as a whole, since it states conclusions without slides to scope them. A third narrative is one more place to disagree, so the draft review checks that it states nothing the methodology reference does not support, and the note stays optional.

Nothing in a finding's numbers bounds how strongly it is worded, and an association read from a scan reads naturally as "X drives Y". Each finding therefore records a claim strength beside its status, and the draft check refuses causal wording above it. The check is a phrase list, not a reading of meaning: it errs toward refusing, since a refused phrase can always be reworded, and it skips the slides that describe method, data, and caveats, where "due to a feed outage" states a fact about the data rather than a finding. A caveat bullet on a finding slide is still read with its finding, so it names an alternative explanation without causal wording ("the rise coincides with a feed outage"). A finding slide takes the weakest claim among the results its methodology section cites, so a causal result cannot lend its strength to an association beside it. Every draft check but the number check reads every narrative as it renders, through one shared reading, so a comment, a fence, or emphasis cannot hide wording from one check while another counts it. That reading covers a stated Markdown subset, and a block form outside it is refused rather than guessed at.

An earlier format packaged a journal that served both as the internal record of decisions and as source text for the audience document, and M365 built its report by narrativizing it, carrying file and column names into delivered documents. Separating the two documents keeps that internal record out of what M365 renders.

The delivered output is a PowerPoint deck rather than Word and Excel documents, because a deck's conceptual outline is easier to check than a report's. The findings document is therefore written as the deck's slide-by-slide outline: each slide has a one-sentence headline with its number, a few bullets, caveats on the slide they qualify, and speaker notes, so the user checks the storyline by reading the headings before M365 builds anything. Its **Answer** slide is the executive summary; M365 no longer distills one. The title slide holds only the deck title and subtitle, and the **Answer** slide follows it, so the two never merge; the headline step says so in one sentence, since users asked to merge them.

A deck's required slides used to be implied by the template, so a request for about eight slides became eleven or twelve, and agents called slides mandatory that no check required. The required slides are now the title, **Answer**, at least one finding, **How we know**, and **Limitations and open caveats**, which lists every represented flagged finding; `check-draft` refuses a deck that lacks one or puts them out of order, and the template marks every other slide conditional or optional. A closing appendix holds slides kept for reference, where **How we know**, **Limitations and open caveats**, **Supporting datasets**, and individual findings may move, and the builder opens it with a divider slide. The brief's Audience section records a length the user asks for, and the headline step reports the main and appendix slides against it and proposes what moves.

The order of finding slides is derived from the question ledger, but the only way to change it was to change a question's priority or parent, which also decides what the **Open questions** slide lists, so a user who wanted one finding first had to demote a question. The derived order is now the default the headline step proposes, and an order the user approves instead is recorded in the manifest's `presentation_order`, which `check-draft` holds the finding slides to and which keys on finding headings, so a renamed finding is refused rather than left silently stale.

The headline step used to stop every new draft for a preview, even when the user had supplied the storyline and asked for the full draft. Reviewing a finished draft meets the same goal, checking the storyline before M365 builds anything, so it has two modes: preview-and-wait, the default when the user has not supplied a storyline, and draft-then-review, which writes the full draft with its headlines marked provisional. A stated preference is recorded in the brief's Audience section for later packages, but a request that names a mode gets it, and one that supplies the storyline or asks for the full draft gets draft-then-review, so an earlier preference never brings back the stop that request asked to skip. A consequential open choice still stops the draft in either mode, asked in the same message, and draft-then-review risks a full rewrite when the storyline is rejected, which is why preview stays the default otherwise.

The workbench ships no figure style. An earlier visualization skill rendered PNG figures to a shared style; its chart forms, style, and honest-display rules now live only in the deck rules, and the builder draws native, editable charts. The plotted numbers stay upstream: each chart is a specification in the findings outline (form, comparison, highlight, axis, interval, source, caveat, alt text) plus one CSV of exactly the plotted values, serialized from a recorded result and refused when that result is stale, as datasets are. The builder draws from that file and never aggregates, so every number on a slide still traces to a recorded result. A chart that plots some of a result's rows, such as a top ten, selects them in its export, the first n rows of the result's stable order or the rows holding given values, instead of needing a recorded result of its own, which once forced twenty-one results to refresh for one six-bar chart; the manifest records the selection, and `check-draft` reapplies it with the recorded labels, percent scaling, and rounding and refuses a chart file that differs, so a file trimmed or rounded by hand never ships; it also refuses an entry whose headers, labels, or percent columns are not what `foundation/display.toml` gives, so an edited entry cannot vouch for an edited file. Rounding is required wherever a column would show more than four decimal places, because unrounded values reached an audience; the number check still traces narrative numbers to the unrounded recorded values, within rounding. Display names stay global per column, since most columns mean one thing across results, with per-result names for a column that does not, and export warns when one name labels results that answer different questions, the case that once mislabeled a dataset silently. The percent list is global for the same reason, and a result whose column of that name already holds percents takes its own list, so its values are not scaled a hundredfold again.

## Deck contract and the M365 handoff

The deck contract is renderer-neutral. `findings.md` stays the single readable source of the deck; the packaging helper derives the slide structure from it when it needs one and never keeps a second copy. The deck rules state what any builder, a person, an agent, or a script, does with the outline and chart files, and each builder's own steps live in its assembly file, so Microsoft 365 is one adapter rather than the contract. `check-draft` checks the rules a parse can settle (the required slides and their order, headline length, bullet count, notes, chart forms, and each chart's named columns in its file), and a reference renderer in the repository's tests builds a deck from a parsed outline, proving the contract complete without Microsoft 365. That renderer is not shipped; whether one ever ships is an open decision.

The approved direction is the workbench to M365. Each package contains a complete findings outline, an internal methodology reference, and any accompanying methodology note, chart files, datasets, and assembly instructions. In the Microsoft 365 Copilot app, the PowerPoint agent's role is building and styling the deck from the outline and drawing each chart from its file; the datasets and any methodology note are delivered beside the deck. It asks the requester before building when the audience or decision differs, a slide will not fit, a chart cannot be drawn as specified, or the effect of a caveat is unclear, and it consults the methodology reference only to understand a decision, never copying its identifiers onto a slide. Reverse synchronization from M365 is out of scope; substantive narrative revisions belong in the package sources. Users did not find the attach list and build prompt among the package files, so each draft carries a `START-HERE.md` that sorts its files into what goes to the audience, what builds the deck, and what stays internal. `check-draft` writes it rather than `export`, because `export` runs before the narratives and any methodology note are final, and `check-draft` runs last, before the inventory that then lists it.

## Workflow responsibilities

Keep the skills as agent-agnostic folders under `.agents/skills/`. Keep generated project behavior in root AGENTS.md; do not generate vendor-specific instruction bridges or require project-local skill installations. Git is required for code history, but GitHub hosting is not. One deliberate exception ships with the skills: a VS Code `.agent.md` package reviewer installed at user level in the Local harness's profile storage. It scopes the reviewer to file read/search tools and the MCP server's read-only tool, and is never generated into a workbench project.

Keep initialization and packaging as separate skills. Initialization establishes the workspace and conventions. The project's AGENTS.md governs everyday analytical work and automatic recordkeeping. The packaging skill creates or revises packages only when explicitly invoked.

Request-gated capabilities were invisible to the analyst because their trigger phrases lived only in agent-facing instructions. Each user-initiated action with its own procedure and gate is therefore a skill, and every skill name carries the `awb-` prefix so the actions group together in hosts that list skills as commands: `awb-init`, `awb-scope`, `awb-brainstorm`, `awb-status`, `awb-clean`, `awb-explore`, `awb-package`, and `awb-release`. Cleaning and exploration work one dataset at a time on either side of the preparation/EDA boundary: `awb-clean` changes shared canonical data and flags affected findings, `awb-explore` reads canonical data within one investigation, hands shared problems to `awb-clean`, and records a confirmed coverage gap as an open quality row, since no correction can fill missing periods. Universal invariants and routing stay in project AGENTS.md. Acquisition and analysis procedures live in project-local workbench-guides, read before their applicable operations. Investigation scoping is its own skill, `awb-scope`, reversing an earlier decision that kept it inside `awb-init` because a separate investigation skill "would add a choice at the moment of starting without serving a distinct need." That held while scoping ran once, when an investigation began. The question ledger made it recurring: the user returns to answer open questions, to collect a stakeholder's answer, or to rescope, and each of those loaded a skill whose body was mostly installation, ignore-rule merging, and the host instruction-file check. `awb-scope` now starts, sharpens, and rescopes investigations and owns their records; `awb-init` sets up, repairs, and upgrades the workspace, asks a new project's question in one line before writing any file so the question still bounds preparation, and hands it to `awb-scope`. A new project loads both skills once; every later question loads only `awb-scope`. Pivots and scope changes stay inside `awb-scope` rather than becoming a third skill: deciding whether an ask extends an investigation or starts another is an interview over the brief and ledger, and the general rule for that boundary is still an open question, which a dedicated skill would press to settle. The name avoids "grill", which other installed interview skills trigger on, and which would invite the `CONTEXT.md` and ADR conventions the workbench excludes. `awb-brainstorm` proposes questions from the ledger, findings, and catalog and runs no queries, so it stays cheap and separate from exploration. Releasing is separate from packaging so that invoking the release skill is itself the explicit delivery request; the packaging skill remains the single owner of the draft layout, manifest fields, and consistency rules. Because `deliveries/` is excluded from Git, the release skill asks for and records the release storage location and copies each release there when reachable. Gates remain description-based, because user-only invocation requires vendor-specific frontmatter.

Bringing a workbench up to date after newer skills are installed is part of `awb-init`'s repair; a separate `awb-update` skill was removed. The agent cannot tell an earlier shipped copy of a helper, package-format file, workbench guide, or the references README from one the project customized without a record, so that check stays mechanical: the installer writes a receipt (`.awb-receipt.json`, path to SHA-256) of every file it installs or replaces, and `--upgrade` replaces only files whose checksum matches their receipt entry, reports customized copies for the user to decide, and removes retired unmodified files only when asked. Adapted files (`AGENTS.md`, `README.md`, `.gitignore`) are edited for each project, so no record can recognize them; repair has the agent reconcile them against the current templates. Folding the update into repair leaves one fewer always-loaded skill description and no per-release list of instruction migrations to accumulate: the current templates are the single target.

The receipt replaced an earlier repository-side record of every shipped version, which had to be regenerated after each asset change and guarded by a test; the project-side receipt needs neither. A refine pass with a second model lineage also removed the per-package `audit/` records (they sat in the Git-ignored `deliveries/` folder, were never copied to release storage, and nothing read them), merged the packaging helpers into one standard-library `draft.py`, folded `draft-provenance` into `export`, and narrowed evidence to the code that computes each result, so repairs and edits to unrelated results no longer mark findings stale.

That narrowing still counted every file in an investigation folder outside its records. `run.py` held every producer, so registering one result's producer staled every result, and so did editing a note or a `methodology.md`; in the 2026-10-15 UX simulation this churn of reruns, promotions, and reviews was the largest cost in agent time. Producing code is now an allow list: `run.py`, the result's own queries, its producer module `producers/<result-id>.py`, which `run.py` loads by result ID so that adding a result never edits it, the files its settings table declares in `code = [...]`, and `src/` except the helpers that only dispatch, record, or package. The allow list's risk is a missed dependency, which would let a stale result read as current. Every other file a producer imports or reads, and every file a result's query reads directly, such as a lookup CSV, is therefore declared, and the analysis guide says so; a declared path must be a file, since a directory would record only the files it held at recording and miss one added later; a producer module is recorded before it exists, so writing one stales its result; and a `run.py` edit still stales every result, since it changes only with the harness. `src/` also still stales every result: following imports through it would narrow that further, at the cost of a reader whose misses would be silent, and is left out deliberately. Parameters are scoped the same way: evidence records the `[parameters]` a result's queries name as `$name` and those its table lists, and `run.py` hands a producer only those, so a read of any other fails instead of escaping the comparison. Evidence scopes them only when `run.py` passes the mapping its producer received: the installer upgrades the provenance helper but never an adapted `run.py`, and an older `run.py` still hands its producers every parameter, so its evidence records every one.

One gap is known and accepted: a chart CSV reused across package revisions is attributed to its result's current evidence, even when the result was rerun after the file was written. `check-draft` now refuses a chart file that no longer equals its result's saved table under the recorded shaping, so the gap is limited to a rerun that left the table unchanged and to dataset files, which it does not compare. Closing it would mean recording which run produced each exported file; a revision that reruns a result should re-export it.

Release trusts `check-draft --verify-only` as its structural gate. `awb-package` runs every structural check before `check-draft` writes the manifest inventory, and the gate reruns every mechanical check and verifies every file but the manifest against that inventory (`awb-release`'s **3. Release** states it), so the releasing agent does not reread the package contract or repeat those checks itself. What can change after packaging is findings flagged since drafting, the dispositions they need, and rules appended to `foundation/review-rules.md`. Release therefore runs the whole review brief again, its narrative checks included, rather than a part chosen for what changed: the reviewer subagent rereads the narratives in its own context, so the releasing agent still reads neither the contract nor the narratives; only in a host with no subagents does the releasing agent follow the review brief itself and read the narratives. A rerun result whose values no longer back the narrative numbers can also change after packaging, and the gate's number check refuses that draft back to packaging. The `release` command runs that gate itself before copying. The releasing agent also runs it once with `--verify-only` before `release`, only to show the user its informational draft markers: a release copies the draft byte for byte, and a DRAFT title an agent wrote once survived into a numbered release. Its report lists the open caveats the release carries, the headline and bullets of the deck's limitations and open questions slides as well as flags released with their caveat, because a release was once reported with nothing outstanding while the deck still stated an open caveat, and a limitations slide may state its one caveat in its headline alone.

The agent that wrote a draft used to be the only one to review it, with full write access, and the user's corrections during review ("never compare partial months") lived only in chat. Packaging and release therefore run the narrative review in a fresh subagent limited to read tools, which reports and never fixes, and keep every correction later drafts could repeat as a numbered rule in `foundation/review-rules.md` that each later review checks; a one-off edit to one draft is not a rule, which keeps the file from filling with notes no later draft needs. Claude Code restricts a subagent's tools through its agent type; a skill's `allowed-tools` only pre-approves tools, and Codex subagents inherit the session's sandbox, so in Codex the restriction is an instruction to a fresh subagent. Only a host with no subagents leaves the writing agent to review its own draft under the brief, the one case where the reviewer is not independent. Bash can still write, so this is a convention plus tool scoping, not isolation. Rule IDs, `R-<area>-NNN`, are never renumbered or reused so that a report, a history entry, or the user can cite one durably; `review-rules add` allocates them. The rule file is Markdown read by the helper, not JSON beside Markdown like `findings.json`, because each rule is one section that `review-rules add` appends whole, and a hand edit changes only a rule's fields, never its ID; a malformed section is reported as a problem, and `add` refuses until it is repaired. A pattern only locates candidate violations: the reviewer judges each match, and a rule without a pattern is judged by reading. Matching line by line turned one wording rule into a verdict per bullet, 13 errors in one run of the 2026-10-15 UX simulation, so a rule may name a scope, `slide` or `document`, and its matches are grouped into one entry per slide or file. A slide is the section a `#`, `##`, or `###` heading opens as the file renders, which is one slide in `findings.md` and one section in the methodology reference and note, so one reading serves every narrative without a slide model for files that have none. `line` stays the default, so existing rules and their reports are unchanged.

Every edit makes a review stale, and a fresh full review after each repair ran to 11 rounds in one run of the same simulation. The reviewer therefore reports every problem in one pass and the writer settles them all, repairing each or reporting a `warning` for the user to accept, before the next review, and within one packaging request a review after repairs may be scoped to the changed lines, the prior report's problems, and rules added or changed since, given the prior report and a diff. Delivery packages are not tracked in Git, so the writer copies what each review reads to a scratch folder and, for a scoped review, diffs the draft against the prior review's copy before replacing it, which catches a change it does not recall, a hand edit included; with no copy, the next review is a full one. A scoped review can miss a problem a repair caused elsewhere, such as a renamed heading that breaks agreement, so it never completes the request: a full review is still required before the request's final `check-draft`, and release runs the full review regardless. The gate keeps its strength and only the intermediate rounds get cheaper.

Agreement and claim strength are not enough on substance: a finding that countries and aggregates sum to the world total had been checked in six years and passed four reviews when the user found a double count in 1991. The review therefore requires every sentence asserting that something was checked, reconciles, sums to, or matches to cite the recorded result or check that establishes it, covering all it asserts; the methodology reference cites the result or evidence, and the audience narratives name the check in plain words. It pairs with `state finding`'s warning on the same wording, which catches a finding when it is written; the review catches every narrative sentence, finding or not.

## Design-session artifacts and generated workbenches

The CONTEXT.md in this design workspace is an artifact of the grill-with-docs session, not a required artifact of an initialized analytics workbench. Omit it from the proposed generated directory structure. The same distinction applies to these design notes: they inform the skills rather than becoming default project scaffolding.

The domain-modeling skill itself introduces CONTEXT.md and ADR conventions; grill-with-docs is the wrapper that invokes it alongside grilling. These software-engineering document conventions are not required analytics deliverables or project records.

Investigation scoping is self-contained in `awb-scope`. Follow the dependent decisions behind the business question and carry settled answers forward. Ask a decision alone when its answer shapes the next question and decisions at the same level together, each with a recommendation; follow up a vague answer at once as a concrete case. An earlier rule asked every independent decision together, which a tool-call audit counted as one round trip, but that audit simulated complete answers; with real answers it recorded vague ones instead of following them up, which is the depth scoping exists for. Resolve facts directly from the environment, and never ask the user a question the data can answer. Finish when scope and purpose decisions are settled in the brief or recorded as open ledger questions, and every material unknown is an open ledger question. Every decision the user can answer is asked before the records are written, and one is recorded open only when the user defers it: in the 2026-10-15 UX simulation, agents that ran setup and scoping in one turn created the investigation and listed the user's own decisions as open questions, which the reporting rule then let them park "to answer now or later". When setup hands the question over in the same turn, the first interview round comes before the investigation exists. Routine implementation choices need no interview. This replaces the external `grilling` dependency and the competing instruction overrides it required.

The workflow instructions must include an analytics-specific adaptation of domain modeling: challenge ambiguous terms, test definitions against concrete examples, check definitions against source data and analytical logic, and record resolved meanings immediately. Shared vocabulary belongs in foundation/glossary.md, local departures in investigation briefs, analytical decisions in investigation histories, and dataset/view descriptions in the foundation catalog. These destinations replace domain-modeling's CONTEXT.md, CONTEXT-MAP.md, and ADR conventions. Incorporate the adapted guidance into the workflow rather than invoking the unmodified domain-modeling skill or grill-with-docs wrapper. The installed skills have not been modified.

## Question ledger

Questions had four homes: the brief's Material unknowns, the state's Unresolved issues, its Next steps (where `awb-explore` wrote untested explanations "as a question"), and chat. Answered ones vanished, so nothing could tell a later brainstorm what had been asked or settled. Each investigation now keeps every question it raises in one ledger, and the other sections narrow: the brief keeps settled decisions, Unresolved issues keeps data problems and coverage gaps (which `awb-status` reads to suggest `awb-clean`, and which no answer closes), and Next steps keeps actions. Folding data problems into the ledger was rejected because a coverage gap never closes and would sit open forever, inflating the counts that drive suggestions.

The ledger is `questions.json` rendered whole to `questions.md`, like `findings.json`, rather than Markdown read by a helper like `review-rules.md`. Status and brainstorming read the JSON directly, and the agent writes nearly every row. The cost is that a stakeholder's answer goes through `awb.py questions answer`, and a hand edit is refused as drift until `questions render` restores it.

A data question is answered only by a recorded result, so the ledger cannot become a second findings table that skips validation and claim-strength guards. The link lives in the result's settings table, `answers = ["Q-NNN"]`, beside the `question` it already requires: evidence recording refuses an unknown ID or a question only a person can answer, and `run.py` marks the question when it records the result, so the link cannot be forgotten and evidence shows which question each result was meant to settle. The ledger stores the link, never numbers; status and resume views read each linked finding's current status, so a flag on that finding shows the answer as unsettled without the ledger holding a stale copy. `answers` computes nothing, so settings comparisons ignore it: adding a link to a recorded result makes it neither stale nor an inexact rerun, and `questions answer --result` links it without a rerun.

Declined brainstorm proposals are kept as `declined` rows so the next brainstorm does not propose them again. An answered question is never reopened or edited: a scope change supersedes it, keeping its answer, and adds a replacement, so the ledger records how the questions changed.

## Glossary ownership

Generated workbenches include `foundation/glossary.md` for shared business and analytical vocabulary. Investigations inherit those definitions. Record investigation-specific meanings or deliberate departures in that investigation's `brief.md`, explaining the difference without silently changing the shared definition or duplicating the full glossary.

Keep definitions separate from scope and configuration: a selected population or reporting period ordinarily changes the investigation's settings, not the meaning of shared terms. The glossary holds terminology; the foundation catalog describes datasets and views. This analytics glossary is distinct from the design session's CONTEXT.md.

## Investigation records

At investigation creation, capture the business question, population or scope, the decision the analysis will support, and what would make the answer useful. Record who will read the delivered documents when the user says; packaging asks for it when it is still missing. Allow an exploratory purpose and explicitly record unknowns rather than requiring a predetermined decision or outcome. Use this brief to guide source relevance and preparation effort.

Separate a concise current-state summary from a chronological history of meaningful learnings and decisions. The current state supports resuming work; the history retains analytical reasoning, caveats, superseded conclusions, and relevant data limitations or errors. Routine debugging, coding mistakes, and abandoned execution attempts that changed no understanding are excluded from both the investigation history and the package's methodology document. A methodological mistake that changed a finding or explains why an earlier conclusion was wrong is retained, because the account must explain how the conclusion was reached. Shared data preparation and quality knowledge remain part of the data foundation.

The agent maintains these records automatically when a finding, decision, or next step changes. Explicit checkpoints are also available before switching investigations.

The findings table and the scan links behind quality rows are machine state that helpers must read back, so each lives in a JSON file beside its Markdown record (`findings.json`, `foundation/quality.json`) rather than inside table cells parsed by pattern. The findings table is rendered from its file and a hand edit is refused as drift, because the promotion guards in `awb.py state finding` mean nothing if the table can be edited around them. The quality record keeps every cell in Markdown, since people write coverage-gap rows and statuses by hand; its file holds only links, keyed by a hash because scan issue keys can embed source values.

When a shared data correction could affect investigation findings, flag those findings and explain the reason. Do not automatically rerun the affected analysis or revise its conclusions. Releases stay frozen.

When work resumes, continue the last active investigation unless the user indicates a switch, and briefly identify that investigation. If a request could fit multiple investigations, ask before changing their records.

## Conversation

Chat carries decisions and results in the user's terms, and bookkeeping stays in files. In the 2026-10-15 UX simulation internal mechanics reached chat in all six runs. The turn footer's example taught ledger tallies, so a user who had asked five questions read that seventeen were answered, because the ledger counts every sub-question the agent adds; and its "(1 needs you)" let a turn announce a question without asking it. The footer and `awb-status` now count the ledger's roots before any sub-question. A count of roots is the user's count only when scoping records each question the user asks as a root and every other question under the one it serves: a stakeholder's threshold or a deferred decision left as a root would be counted as the user's, and an umbrella question above the user's questions would hide them. A question that needs the user is asked in the message that says so, as a plain decision with a recommendation and the alternative. An environment or tool limit is reported only with what it means for the user, since a bare "MCP unavailable" left users unsure whether to act, and the setup report keeps to five items, among them what the user must act on, with its impact, leaving the rest in the installer's JSON and the files; a repair report adds what its reference lists. A first chat answer built from exploration keeps a finding's discipline: a saved query's figure is exploration until `run.py` records it, an untested explanation is a question, what the user recalls is their statement, and a comparison names what it leaves uncontrolled.

The project `AGENTS.md` is loaded in every session, so the words these rules add were cut elsewhere in it, mostly where a template, a guide, or a helper's refusal already says the same; it did not grow. Commits stay on the user's request by default, so the history holds what the user chose to keep; asking before each commit cost a turn every time, so a user who wants analytical code committed as the work goes says so once and the README's `Commits` line records it.
