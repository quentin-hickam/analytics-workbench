## 2. Contradictory, ambiguous, long or missing instructions

- **MCP versus CLI:** AGENTS.md says to use MCP whenever the host offers awb. It does not distinguish an offered server from a callable write capability. CLI fallback was necessary and worked; document this explicitly.
- **Status versus record maintenance:** awb-status says to remain read-only. In the same request, the user accepted findings and gave a durable Cherry Lights presentation instruction. I recorded those authorised decisions separately, then ran the status collector read-only. The skill should explain this combination rather than imply acceptance must remain only in chat.
- **Eight slides versus template sections:** The user controlled slide count and presentation choices. The templates suggest separate slides that would exceed the target. The final format combined content while preserving the eight-slide story.
- **Audience-facing versus internal methodology:** The template explicitly expects codes, paths and precise internal terms, but the user needed a note Finance and leadership could circulate. A two-layer note was missing from the initial design.
- **Headline approval versus autonomy:** awb-package's mandatory checkpoint prevailed over the user's general instruction to go ahead. I obeyed it but it was an extra interaction. An explicit permission-to-draft mode would avoid this conflict.
- **Instruction-file links versus user preference:** The user said they would not open tool instruction files. Higher-priority session instructions nevertheless required naming/linking/quoting a skill whenever it forced a pause. This made the headline checkpoint explanation more mechanical than the user wanted. Prefer a plain decision request, with an expandable provenance reference rather than a required visible link.
- **Packaging serialises evidence, but chart subset support is missing:** A normal display choice became analytical work. There should be a documented, narrow presentation-projection path that does not loosen the evidence contract.
- **First-observed caveat placement:** General slide rules favour visible caveats. The user explicitly wanted this qualification in notes instead of the headline. I honoured that, preserved other ID-coverage caveats visibly, and kept the exact definition in methods.
- **Product-range language:** Grouping seven variants does not establish an aggregate range rate or a ranking of all product lines. Instructions should distinguish grouping labels from aggregation. Similarly, a latest-year customer share is not a customer contribution to country growth.
- **Generic eligibility validation:** A global minimum proportion of source rows is not appropriate for deliberately focused single-account diagnostics. Validation defaults need a documented narrow-diagnostic mode with explicit enumeration and cardinality checks.
- **Git expectations:** The guides suggest commits, but filesystem policy prevented repository creation. I recorded the gap and retained hashes instead of repeatedly asking the user to fix an environment limitation. Add an explicit no-VCS mode.
- **Length and duplication:** The package skill, contract, templates, review reference and helper reference restate many consistency rules. Useful for precision, but costly to navigate. A concise decision tree with links to exceptional branches would help.

## 4. Deviations and judgement calls

- Used the local CLI for all writes after two MCP policy failures. This preserved the intended helper behaviour rather than bypassing its validation; no unapproved external communication or privilege escalation occurred.
- Did not keep suggesting a commit or retry Git initialization once repository creation was known to be policy-prohibited. Recorded unavailable commit provenance and retained producing-file hashes/runtime instead.
- Initialisation included setup and scope; the future deck request was not treated as a reason to start an empty package. Analysis and packaging proceeded when the user subsequently requested them. This staging was defensible, but the initial response should have named the context questions clearly; the user had to ask what they were.
- Recorded user acceptance/presentation guidance during an awb-status turn as separately authorised maintenance, while keeping the status collection itself read-only.
- Combined template sections to honour the eight-slide limit; described audience tables only in closing notes when requested. Preserved caveats and methods rather than adding unwanted slides.
- Narrowed two requested headlines without another permission round: no uncomputed pooled Cherry Lights rate/universal product-line superlative, and no attribution of Australia's growth to a customer when only latest-revenue concentration was measured. The independent reviewer caught the latter before completion.
- Treated top growers as the five already under discussion, plus Ireland, rather than asking another low-value clarification. The user accepted the resulting chart.
- Treated chart selection as a display-only result within the same question/population, not a consequential rescope. Used the required recorded-results route and refreshed affected producing provenance.
- Some early exploratory comparisons used pandas on helper exports and one saved daily CSV. Rebuilt all final recorded diagnostics/sensitivity calculations as saved SQL against canonical data. An accidental dummy SELECT was not used as evidence.
- Did not add a current-assortment filter or infer product defects. Historical relevance remained a Merchandising caveat. Missing IDs were not treated as errors or as one anonymous customer.
- Preserved unverified within-sheet repeats; removed only proven cross-sheet copies after user approval. The audit confirmed all removed copies were in early December 2010 and explicitly disclosed other repeats elsewhere.
- Kept the methods summary to a 360-word one-page-sized opening; did not install document-rendering dependencies or claim a physically paginated PDF existed.
- Delegated only where the package/release skills explicitly require a fresh read-only reviewer. Codex tool restrictions are instructional rather than capability-enforced; each reviewer was explicitly told not to write or run write commands.

## 5. Disproportionate time/token costs

1. **Narrative edits invalidating computation:** finishing methodology caused an all-result refresh, and further producer adjustments repeated it. Original numeric tables remained byte-identical. This was the clearest unnecessary computational cost.
2. **A simple chart becoming a result lifecycle:** six display rows required new SQL, audit, settings, validation, promotion, evidence refresh, chart mapping and selection-record updates. The workbench preserved excellent traceability but lacked a lightweight projection abstraction.
3. **Instruction/context gathering:** the same rules span multiple long skill, contract, template, guide and helper files. Full state output also repeats brief, findings, settings and questions. Truncation led to narrower rereads and context recovery.
4. **Parser-driven repairs:** storyline order and the quality table layout required understanding formatting/inference rather than analytical reasoning. Four quality-record attempts were too many before identifying the structural issue.
5. **Independent review cycles:** an initial package review, fresh review after a wording repair, fresh review for a later revision, and a mandatory new review at release all consumed effort. They found a real unsupported claim, so this was not wasted overall. Cache a review by hashes/rule set for unchanged release requests, or at least provide a persisted review report that the release step can verify.
6. **Manual package bookkeeping:** maintaining exact questions, display mappings, represented-result selections, matching headings and provenance exceptions took appreciable tokens. More explicit machine-readable slide metadata could generate much of this.
7. **Self-inflicted verification noise:** hard-coded expected check counts, README-format assumptions and JSON scalar conversions cost avoidable iterations. Better agent restraint and helper-provided summaries would help.

## 6. What worked well

- Clear foundation/investigation/package boundaries kept originals intact and prevented exploratory assumptions becoming silent shared corrections.
- Source landing/retention and release helpers performed copy, checksum and verification work reliably. Release numbering and the configured external folder worked exactly as requested.
- Evidence records, saved queries/settings, descriptive claim strength and automatic ledger links made findings auditable. Reruns correctly preserved supported/superseded findings when outputs/checks were unchanged.
- Independent review caught the unsupported Australian growth wording that number checks cannot detect. The corrected revenue-concentration claim was materially better.
- Mechanical draft checks caught headings, exact questions, data mappings, numbers, inventory and storyline issues; final checks and stale checks were clean.
- The distinction between missing-ID revenue and customer-identifiable analysis, full first-purchase history across sheets, complete repeat follow-up, and signed cancellation arithmetic prevented important analytical errors.
- The product screen preserved a persistent inconvenient result while removing one-off dominant reversals; cut-offs were explicit recommendations rather than invented business truths.
- The open/parked stakeholder questions let IT/Finance/Merchandising checks remain honest caveats without blocking the package after the user accepted that treatment.
- Review rules captured repeatable user corrections; all five passed the final package and release reviews. Preferred wording for a single slide was treated as an edit, not a universal rule.
- Exact audience dataset selection avoided unwanted customer/product exports. Display mappings and precision settings fixed Excel readability while retaining raw evidence precision.
- The final handoff became actionable once it listed exactly seven PowerPoint attachments and a one-line instruction; the user explicitly accepted it.
- No stakeholder messages were sent, no additional approval was invented at release, and no frozen release contents were modified after delivery.

The biggest improvement would be a smaller, audience-aware package layer with explicit slide metadata and lightweight recorded chart projections, backed by result-specific computational provenance. That would retain the strong audit/release guarantees while reducing repeated computation, instruction reading and user checkpoints.
