### Added

- `read_xlsx` is on the read-only read list, so `sql --read-only`, `profile --read-only`, and the MCP `read` tool can query a landed Excel file through a view (#56). It comes from DuckDB's `excel` extension. The read-only session still installs no extension, but loads one already installed when a statement needs it, with its configuration locked. Without the extension, `read_xlsx` fails on one line saying so and how to install it once through the write path: `python3 src/awb.py sql "INSTALL excel; SELECT 1"`, or the `data` tool's `sql`. `read_xlsx` writes nothing: its arguments name a file, a sheet, a range, and how to read cells, and only `COPY`, which the read path refuses, writes an `.xlsx`. The landing reference lists the read path's file readers and this install step.

### Fixed

- Read-only SQL runs DuckDB's `histogram()` aggregate again (#57). The dynamic SQL check now reads each call's position from the parse tree. A function or table macro that builds SQL from a string (`query`, `query_table`, `json_execute_serialized_sql`, `histogram_values`, the `histogram` table macro) is refused where it is called as a table function, and a scalar macro calling one is refused wherever it is called. So `SELECT histogram(id) FROM orders` runs through `sql`, `profile`, and `read`, and `FROM histogram(orders, id)` is still refused. A view file's CREATE VIEW, CREATE TABLE ... AS, or CREATE MACRO is checked by the parse tree of its body, so a view using `histogram()` as an aggregate loads. Known limit: a CREATE whose body does not parse alone, such as a macro with two bodies or `CREATE TABLE ... WITH NO DATA`, is still checked by token, and `histogram()` is refused there in any position.
- `profile` counts map, list, and struct values, such as a `histogram()` result, by their text instead of failing on `unhashable type: 'dict'`.
