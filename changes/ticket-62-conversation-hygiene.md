### Added

- A `Commits` line in the project README, `on request` by default or `as I go`, which the agent sets when the user asks for commits as it goes. With `as I go` the agent commits analytical code as the work goes, evidence before a rerun, preparation SQL before a publication, and a kept reference document included; otherwise it commits when asked and suggests a commit at most once a session while analytical code is uncommitted, and the analysis and data guides' suggestions before a rerun, a publication, or for a kept reference document count toward that one.
- `collect_status.py` reports `roots`, the ledger's questions with no parent, and `must_subquestions`, the must questions under them, each by displayed status and apart from the totals in `counts`; a ledger question without a string `parent` and `priority` makes the ledger unreadable. `awb-status` leads Open work with them in the user's terms, "Your five questions: 5 of 5 answered", and reports `questions.counts`, which include every sub-question, only on request.

### Changed

- The project `AGENTS.md` turn footer counts the user's own questions, the ledger's roots, when the turn changed any, "Your five questions: 3 answered, 2 open", never ledger rows, and names the next step. Its Conversation section adds three rules: a question that needs the user is asked in that message as a plain decision with a recommendation and the alternative, never by pointing to a skill or instruction file; an environment or tool limit is reported only when it affects the user, with whether they must act and what the workbench does instead; and files are named by path, never said to be attached or sent.
- The project `AGENTS.md` analytical invariants cover first answers built from exploration: a saved query's figure is exploration, an untested explanation is offered as a question, what the user recalls is recorded as their statement, not as confirmed, and a comparison names what it leaves uncontrolled when a decision rests on it. The file stays within its 814 words, and a test holds it there: the added words were cut elsewhere in it, from sentences the state and history templates, the analysis and data guides, or a helper's refusal already state, namely that a hand edit to the findings table is refused, what Unresolved issues and Next steps hold, that only a recorded result answers a data question, and that each failed check is understood before promotion. The rule that intermediate computation stays in views and in-process results, never in CSV files handed between steps, moved to the analysis guide.
- A root of the question ledger is a question the user asked. `awb-scope` records each question the user asks as a root and every other question, such as a stakeholder's threshold, a decision the user deferred, or a method choice, under the user's question it serves, so the roots that status and the turn footer count are the user's own; `awb-brainstorm` leaves a parent empty only when the user takes the question as their own, the project `AGENTS.md` and the analysis guide record a question the work raises under the question it serves, and `awb.py questions add --help` says what a root is. When `awb-scope` sharpens an investigation, it gives a root the user did not ask, which a ledger written before this change may hold, the user's question it serves as parent, first recording the brief's question as a root when the ledger lacks it.
- `awb-scope` asks every decision the user can answer before it writes the records, bundling those at the same level, and records one as an open user question only when the user defers it; its report no longer offers the user's questions "to answer now or later". When `awb-init` hands the question over in the same turn as setup, `awb-scope`'s first interview round is asked in that turn's report before the investigation is created. `awb-explore` asks in its report each question it added that the user can settle, and `awb-brainstorm` each kept question the user can settle, sending only a stakeholder's question and a scope change through `awb-scope`.
- The `awb-init` setup report has at most five items: the project root, the question handed to `awb-scope` with its first interview round, any host instruction file with its import line, each item the user must act on with its impact, and the next request. Files created or preserved and deferred directories stay in the installer's JSON and the files. A repair report adds what `references/repair.md` lists.
- `awb-status` reports Git being unavailable with its reason and what it means for the user: status cannot tell what is uncommitted or whether the state is out of date, evidence records file checksums instead of a commit SHA, and whether the user must act.
- The package and release reports state a provenance gap as what went unrecorded, such as "the Python version for one result was not recorded", or leave it out when it changes nothing the user decides.
