### Added

- `install_helpers.py` records the interpreter it runs under on the project README's `Project interpreter` line, project-relative inside the project and absolute outside it, inserting the line after `Commits` (else `Active investigation`) when the README lacks it. Its JSON reports the line, whether the interpreter is `in_project`, and its status: `written`, `current`, `replaced` (with `was`, a value that named no file), or `missing` under `--check`. A README naming another interpreter that exists, or repeating the line, refuses with exit 1 and nothing written: rerun with that interpreter, or edit the line to switch. The README template gains `Project interpreter: not yet recorded` and `Code history: Git`.
- `src/awb.py` reruns itself under the project's interpreter when another one starts it: `AWB_PYTHON`, else README's `Project interpreter`, else the project's `.venv` or `venv`. It says so on stderr, reruns at most once, and names a README line it cannot use (repeated, empty, or naming no file) before going on to the next. The MCP server runs every command under the same interpreter, read by the same function.
- `record_cleaning.py` decisions take a `new` list of issues the scan did not report, each with object, observation, evidence (a saved query's project-relative path, which must exist, or a reference in words), and the judgment columns, and optionally correction, change, findings, and check. Each gets the next ID, its evidence after the observation, and no scan marker or `quality.json` link; `{N1}` names the first entry's ID in other text, and running the call again finds its row instead of adding another. The MCP `records` tool's `clean-record` passes it through, and the tool's description names it.
- A no-Git mode: when Git is absent or `git init` fails, `awb-init` records `Code history: none (<reason>)` on a README line and reports it once, and the agent makes and suggests no commits while it says so.
- Archive and spreadsheet landing in the landing reference and the data guide: land an archive as received, with the members a conversion reads extracted beside it in the same `land` call and `--notes` naming the archive as the original; publish a workbook through DuckDB's `read_xlsx`, from the `excel` extension, with `all_varchar = true`, converting Excel serial dates explicitly from `DATE '1899-12-30'`, or `DATE '1904-01-01'` for a 1904-system workbook.

### Changed

- The install hint is `uv pip install --python <python> <packages>` when the interpreter has no pip and its `pyvenv.cfg` records uv or uv is on the path, and a written `requirements.txt` header names the same command; otherwise both are unchanged.
- `awb-init` runs the printed install command itself when the interpreter is inside the project, such as its virtual environment, and reports it in one line; it asks before installing anywhere else.
- Quality IDs default to `DQ-NNN`, distinct from the ledger's `Q-NNN`; a quality record already numbered with another prefix, `Q-` included, keeps it. `record_cleaning.py`'s help and `awb-clean` use `DQ-004` as the example.
- The `quality.md` template keeps its guidance above each table and names the two sections `record_cleaning.py` reads, which are kept as written, and the `DQ-NNN` format.
- The project `AGENTS.md` Commands section states the fallbacks: when a write tool is refused or unavailable, run its CLI command, keep using the tools that work, and say so once; skill scripts run by path, never as `awb.py` commands; and `python3` in every workbench command means README's `Project interpreter`. Words were cut elsewhere in it, and the file stays at 814 words.
- `record_cleaning.py` refuses a decisions key other than `date`, `issues`, `new`, `findings`, `flags`, and `catalog`, which it used to ignore.

### Fixed

It used to skip such rows, report a decision naming one as "issues not in the scan", and could give a new row an ID they already held.
